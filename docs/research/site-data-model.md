# site-data-model

## Summary
A "full site" in Nautobot 2.x is a graph of roughly 25-30 model types split into two sharply different categories: site-scoped objects that a clone must CREATE (Location subtree, RackGroups/Racks, PowerPanels/PowerFeeds, Devices + their components, Modules, Cables, Prefixes, IPAddresses, VLANs, VRF-prefix assignments, IPAddressToInterface rows, RelationshipAssociations, local config context) and shared/global definitions that a clone must REFERENCE by natural key and never duplicate (Status, Role, Tag, CustomField, Relationship, Manufacturer, DeviceType + component templates, ModuleType, Platform, Tenant, SecretsGroup, Namespace, VLANGroup, ConfigContext). The dependency graph is a mostly-clean DAG with three well-known cycles/quirks: Device.primary_ip4/6 must point to an IP already assigned to one of the device's own interfaces (forcing a two-phase device write), VirtualChassis.master vs Device.virtual_chassis, and intra-model self-FKs (Location parent chain, Interface lag/parent/bridge, FrontPort→RearPort). Cables are pure glue: generic-FK endpoints, uniqueness per endpoint, and — critically — Cable's natural key is literally ["pk"], so cabling must be serialized as (device-name, component-name) endpoint pairs, i.e., as a topology pattern, not as identifiable objects. VLAN also falls back to pk as its natural key (nullable vlan_group), and IPAddress identity is (namespace, host) with a mandatory parent Prefix, so prefixes must exist before IPs and namespace choice is a required clone parameter.

The single biggest replay trap is component auto-creation: Device.save() automatically instantiates every component from the DeviceType's templates (in a fixed order: console ports, power ports/outlets, interfaces, rear then front ports, device bays, module bays). A naive export-everything/replay-everything therefore double-creates or collides on (device, name) uniqueness. The correct pattern — for BOTH proposed options — is: create the device (letting templates fire), then UPDATE template-born components by name with per-site overrides (mode, VLANs, descriptions, LAG membership, mgmt_only), create only the delta components that don't come from templates, and record deletions. This also means the export job must diff each live device against its current DeviceType templates, and must handle template drift (devices created before the DeviceType was edited won't match today's templates). Both options face the identical serialization problems (ordering, natural keys, component diffing, IP re-mapping); Design Builder does not solve any of them for you — it has no reverse-engineering/exporter feature at all — but its runtime does give sequential top-down processing with !create_or_update/!update/!ref semantics that natively express "create device, then patch its auto-created interfaces, then set primary_ip in a second pass", plus deployment lifecycle (tracking, decommission, data protection) as its genuine value-add. Known open bugs (import mode broken with the connect_cable extension #184, rack-position idempotency #207) sit exactly on this project's critical path and should be verified.

Version context matters for the decision: as of July 2026 Nautobot 3.1 (Apr 2026) is current stable and 2.4 is LTM; Design Builder is actively maintained with v3.1.1 (June 23, 2026) for Nautobot 3.x and a v2.3.x branch (min Nautobot 2.4.20) in critical-fixes-only mode. Genuinely parameterizable clone inputs are: site/location names + naming patterns for devices/racks, IP space via supernet-to-supernet offset mapping (preserve host offsets; rewrite Prefixes, IPAddress hosts, and follow through to primary IPs), VLAN IDs (map/offset; a new VLANGroup is mandatory since VLANGroup names are globally unique), and target Namespace. Serial numbers, asset tags (unique), and MACs should be dropped; device types, roles, platforms, statuses, rack elevations, interface layouts, and cable topology carry over verbatim as references/patterns. Cross-site edges (circuits, inter-site cables, relationship associations pointing outside the subtree, location-scoped ConfigContexts that won't auto-apply to a new location) must be detected and either flagged or skipped.

## Details
# What "a full site" is in Nautobot 2.x, and what makes it hard to serialize/replay

Research conducted July 2026 against primary sources: Nautobot core source (develop = 3.x line and ltm-2.4 branches on GitHub), docs.nautobot.com, and the nautobot-app-design-builder repo/docs.

## 0. Version context (affects everything below)

- Nautobot release train ([release notes index](https://docs.nautobot.com/projects/core/en/stable/release-notes/)): 2.0 (Sep 2023, IPAM Namespaces, generic Role, IP-to-many-interfaces), 2.1 (Dec 2023), 2.2 (Mar 2024, Controllers, Software versions), 2.3 (Aug 2024, **Device Modules**, Cloud models), 2.4 (Jan 2025, Virtual Device Contexts, Wireless) — **2.4 is the LTM line**. **3.0 shipped Nov 2025** (Bootstrap-5 UI, approval workflows, LB/VPN models) and **3.1 (Apr 2026) is current stable**. The DCIM/IPAM data model described below is essentially the same across 2.x→3.1, but natural-key behavior for Device changed on develop (see §3).
- Design Builder ([releases](https://github.com/nautobot/nautobot-app-design-builder/releases)): v3.1.1 (2026-06-23) for Nautobot 3.x; v3.1.0 (2026-04-12, added `next_ip` action tag); v2.3.0 (2025-12-09, min Nautobot **2.4.20**, LTM branch, critical fixes only). The app is alive and tracking core releases. It has **no exporter/reverse-engineering capability**; its v1.4 "import" feature only lets a deployment *claim ownership* of objects that already exist.

## 1. The object graph for a complete site

### 1a. Site-scoped objects (a clone CREATES these)

Rooted at one Location subtree:

- **Location tree**: `Location` rows forming the site (e.g., Site → Building → Floor → Room). Name is unique **per parent** (`unique_together (parent, name)`); root-level names unique among roots. The `location_type` of a Location **cannot be changed after creation**, and parent/child type rules are validated in `clean()` (nestable flag, parent-type matching). Source: [locations.py](https://github.com/nautobot/nautobot/blob/develop/nautobot/dcim/models/locations.py).
- **RackGroup** (tree, unique per (location, name)) → **Rack** (unique per (rack_group, name) and (rack_group, facility_id); `clean()` validates rack_group.location is an ancestor of rack.location). Source: [racks.py](https://github.com/nautobot/nautobot/blob/develop/nautobot/dcim/models/racks.py).
- **PowerPanel** (unique per (location, name), optional rack_group) → **PowerFeed** (unique per (power_panel, name) and (power_panel, breaker_position); is a cable-termination endpoint). Source: [power.py](https://github.com/nautobot/nautobot/blob/ltm-2.4/nautobot/dcim/models/power.py).
- **Device** (unique per (location, tenant, name), plus (rack, position, face) and (virtual_chassis, vc_position)). Carries FKs to shared objects (device_type, role, platform, status, tenant, secrets_group, software_version, device_redundancy_group + priority, controller_managed_device_group) and site objects (location, rack), plus `local_config_context_data` (JSON) and `_custom_field_data`. Source: [devices.py](https://github.com/nautobot/nautobot/blob/develop/nautobot/dcim/models/devices.py).
- **Device components**: Interface, ConsolePort, ConsoleServerPort, PowerPort, PowerOutlet, FrontPort, RearPort, DeviceBay, ModuleBay — **auto-created from DeviceType templates on `Device.save()`** for new devices (see §5). Since 2.3, most components are `ModularComponentModel`: they belong to **exactly one of** a Device or a Module (both FKs nullable, validated), unique on (device, name) AND (module, name), natural key `[device, module, name]`. Interface additionally has self-FKs `lag`, `parent_interface`, `bridge`, an IPAM `vrf` FK, `mode`/`untagged_vlan`/`tagged_vlans` (m2m), `mac_address`, `mgmt_only`. FrontPort has `rear_port` FK + unique (rear_port, rear_port_position). Source: [device_components.py](https://github.com/nautobot/nautobot/blob/develop/nautobot/dcim/models/device_components.py).
- **Module** (2.3+): installed in ModuleBays, itself has ModuleType with its own component templates; module component names are rendered with `{module}` / `{module.parent}` position placeholders (`render_name_template()`), so component names are a function of bay position.
- **Cable**: generic-FK endpoints `termination_a_type/_id`, `termination_b_type/_id` (ContentType limited to CABLE_TERMINATION_MODELS: interfaces, console ports/server ports, power ports/outlets, front/rear ports, power feeds, circuit terminations), `unique_together` on each endpoint pair (one cable max per endpoint), status FK, type/label/length/color. **`natural_key_field_names = ["pk"]`** — cables have no business-level identity. `CablePath` (the traced end-to-end connectivity) is a computed cache and must never be exported — it is rebuilt by signal logic (`from_origin()`), including front/rear-port position walking. Sources: [cables.py](https://github.com/nautobot/nautobot/blob/develop/nautobot/dcim/models/cables.py), [cable docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/core-data-model/dcim/cable/).
- **IPAM**: 
  - **Prefix**: unique per (namespace, network, prefix_length); `type` field ∈ {Container, Network, Pool}; parenting (tree) is **automatically managed** at the DB level in 2.x; `locations` is m2m in ≥2.2. VRF association is m2m (`VRFPrefixAssignment`).
  - **IPAddress**: **mandatory parent Prefix FK**, auto-resolved to the closest matching prefix in the Namespace during `clean()`/`save()`; creation **fails if no suitable parent exists**. Unique per (parent, host); natural key (parent__namespace, host). Duplicate IPs are legal across Namespaces, illegal within one. Sources: [ipam models](https://github.com/nautobot/nautobot/blob/ltm-2.4/nautobot/ipam/models.py), [IPAM what's-changed](https://docs.nautobot.com/projects/core/en/stable/user-guide/administration/upgrading/from-v1/ipam/whats-changed/).
  - **IPAddressToInterface** (through model): unique (ip_address, interface); boolean role flags `is_source, is_destination, is_default, is_preferred, is_primary, is_secondary, is_standby`. Interface↔IP is m2m in 2.x (one IP can sit on many interfaces).
  - **VLAN**: unique per (vlan_group, vid) and (vlan_group, name) — but `vlan_group` is **nullable**, and the code comments admit NULL≠NULL allows duplicates, so **VLAN's natural key is `["pk"]`**. `locations` m2m via VLANLocationAssignment. **VLANGroup.name is globally unique** (has optional location FK and a `range` field defaulting "1-4094").
  - **VRF**: unique per (namespace, rd); rd nullable (same NULL caveat); prefixes m2m.
- **Metadata rows**: `_custom_field_data` JSON on every object (definitions are global); `RelationshipAssociation` rows (content-type + PK on both sides — must be resolved to natural keys and may point outside the site); tag assignments (m2m); object metadata (2.3+); Notes; dynamic-group membership (computed from filters — do not export).
- **VirtualChassis** if present: VC has `master` FK to Device while member Devices have `virtual_chassis` FK + `vc_position` — a create-order cycle (create VC without master → assign members → set master).

### 1b. Shared/global objects (a clone REFERENCES these — duplication is a bug)

Status, Role, Tag (each scoped by `content_types` m2m — a referenced Status/Role must have the target model's content type enabled), CustomField definitions (+ choices), Relationship definitions, ComputedFields, Manufacturer, **DeviceType** (unique (manufacturer, model)) **with all its component templates**, ModuleType, Platform (name unique; network_driver/napalm fields), Tenant/TenantGroup, SecretsGroup (+Secrets — never export secret values; reference the group), Namespace (name unique), VLANGroup (name unique — see §4), RIR, ConfigContext/ConfigContextSchema, GitRepositories, JobHooks/Webhooks. ConfigContexts are global, rule-scoped objects (m2m: locations, roles, device_types, platforms, cluster_groups, clusters, tenant_groups, tenants, tags, device_redundancy_groups, dynamic_groups + weight) — see pitfall §5.6. Source: [extras models](https://github.com/nautobot/nautobot/blob/ltm-2.4/nautobot/extras/models/models.py).

App-owned models (BGP `AutonomousSystem`/peerings, Device Lifecycle, Golden Config settings, Floor-plan app, etc.) are **outside core** — note that core Nautobot has **no ASN model**; ASN parameterization implies the BGP app is in scope, which extends the graph.

## 2. Dependency ordering (FK DAG + cycles)

A working topological order for replay:

1. **Tier 0 — shared references** (verify-or-fail, never create silently): ContentTypes, Statuses, Roles, Tags, CustomFields, Relationships, Manufacturers, Platforms, DeviceTypes(+templates), ModuleTypes, Tenants, SecretsGroups, Namespace, VLANGroup(s).
2. **LocationType chain** (usually exists) → **Location subtree** in parent-first order.
3. **RackGroups** (tree order) → **Racks**; **PowerPanels** → **PowerFeeds**.
4. **Prefixes** — create containers/supernets before children for a sane tree (parenting is auto-managed but parents must exist for IPs); **VLANs** (group first); **VRFs** → VRF↔Prefix assignments.
5. **Devices** (components auto-create here) → **Modules** into module bays (bay-position order; nested modules parent-first) → **component fix-ups**: create non-template components, update template-born ones; order intra-device: RearPorts before FrontPorts; LAG/parent/bridge interfaces before their members.
6. **IPAddresses** (parents exist by now) → **IPAddressToInterface** rows (needs both IP and interface).
7. **Device.primary_ip4/primary_ip6** — second-pass update; `Device.clean()` enforces the IP is already on one of the device's interfaces ("The specified IP address is not assigned to this device").
8. **Cables** — both endpoints must exist; CablePaths regenerate via signals.
9. **VirtualChassis master fix-up; RelationshipAssociations; local config context; redundancy-group priorities.**

**Cycles / near-cycles:** (a) Device→primary_ip→IPAddressToInterface→Interface→Device (solved by deferred update, step 7); (b) VirtualChassis.master ↔ Device.virtual_chassis; (c) self-referential ordering: Location parents, RackGroup tree, Interface lag/parent_interface/bridge, FrontPort→RearPort; (d) Prefix parent tree — not a real cycle (auto-computed) but IP creation hard-fails without a parent prefix in the namespace.

Design Builder's runtime can express all of these: YAML is processed sequentially, `!ref` stores handles to created objects, and a later `!update` entry on the same device sets primary_ip; cables use the contrib `connect_cable` extension ([design development docs](https://docs.nautobot.com/projects/design-builder/en/latest/user/design_development/)).

## 3. Natural keys in Nautobot 2.x — who has usable identity

Nautobot 2.0 gave every BaseModel `natural_key()`/`get_by_natural_key()`, auto-derived from uniqueness constraints; composite-key URLs were removed from user-facing API/UI, and CSV moved to multi-column natural keys ([2.0 release notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.0/), [natural-keys dev docs](https://docs.nautobot.com/projects/core/en/stable/development/core/natural-keys/)).

| Model | Natural key | Notes |
|---|---|---|
| Location | name + **variadic ancestor chain** (`parent__name`, `parent__parent__name`, ...) | `LOCATION_NAME_AS_NATURAL_KEY` opt-in simplifies to `name`. Depth-dependent — see §5.7 |
| Device | 2.x: `[name, tenant, location]` (location variadic); `DEVICE_NAME_AS_NATURAL_KEY` → `[name]` | 3.x develop: `DEVICE_UNIQUENESS` setting; **default natural key `["pk"]`** (medium confidence; verify against the 3.1 tag) |
| Components (Interface, etc.) | `[device, module, name]` | Module-hosted components need module identity (bay position chain) |
| Rack / RackGroup | `[name, rack_group]` / `[name, location]` | |
| DeviceType | (manufacturer, model) | Shared — reference only |
| Prefix | (namespace, network, prefix_length) | derived from unique constraint |
| IPAddress | (parent__namespace, host) | |
| VLAN | **`["pk"]`** — no usable natural key when vlan_group is null | Put site VLANs in a VLANGroup to get (group, vid) identity |
| VRF | (namespace, rd), rd nullable | same NULL caveat |
| Cable | **`["pk"]`** | identity only via its two endpoints |
| Status/Role/Tag/Platform/Tenant/Namespace/VLANGroup | unique `name` | clean references |

**Consequence:** an export format keyed purely on natural keys works for ~90% of the graph but *must* invent synthetic identity for Cables (endpoint pair), VLANs (group+vid or exported ordinal), and group-less VRFs. Component templates are identified by (device_type, name) and must never be re-emitted per device.

## 4. What is genuinely parameterizable when cloning a site

- **Names**: new site/location name (subtree node names usually carry over); device and rack names via pattern rewrite (e.g., regex `^OLD-` → `{new_site_code}-`, or a format template). Since Device uniqueness is (location, tenant, name), keeping source names verbatim is *technically* legal in a new location, but pattern renaming is what users will want.
- **IP space (re-prefixing)**: map each source top-level supernet → target supernet, preserving prefix lengths and host offsets: `new_host = new_net_base + (old_host − old_net_base)`. Rewrite Prefixes first, then IPAddress hosts; interface assignments and primary-IP pointers follow the map automatically because they're object references. Two viable strategies: (a) same Namespace + re-prefixing (typical enterprise plan), or (b) new per-site **Namespace** with verbatim IP reuse (Nautobot 2.x explicitly supports duplicate IP/prefix space across namespaces) — the tool should offer both; (b) needs zero math but changes routing semantics.
- **VLANs**: vid offset/map; **must** create a new VLANGroup (names globally unique) e.g. `{site}-vlans`; interface untagged/tagged references follow the object map.
- **ASNs**: only if BGP app in scope (no core ASN model).
- **Drop/blank on clone**: `serial`, `asset_tag` (unique constraint!), interface `mac_address`, rack `facility_id` (unique per group), circuit references, timestamps, all PKs, CablePaths, dynamic-group memberships.
- **Carry verbatim (as references or patterns)**: device_type/role/platform/status/tenant references, rack elevations (position/face/u_height), interface layout (implicit via DeviceType templates + explicit deltas), cable topology as (device-ordinal, port-name)↔(device-ordinal, port-name) pairs, power feed wiring, local config context JSON (optionally with Jinja-ized site variables), custom-field values (with a per-field include/exclude hook — some CF values are site-specific like "site code").

## 5. Pitfalls (both options hit all of these)

1. **Template auto-creation double-create**: creating a Device fires `create_components()` from DeviceType templates ([devicetype docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/core-data-model/dcim/devicetype/): components are generated automatically; later template edits do NOT retro-apply to existing devices). Replay must: create device → **update** template-born components by name (mode, VLANs, descriptions, LAG membership, enabled, mgmt_only, vrf) → **create only** delta components → **delete** components the source device removed relative to the template. The export must therefore compute a three-way component diff (live device vs current templates), and must handle **template drift** (source devices created before the DeviceType was edited). Note the REST API and Design Builder both go through `save()`, so both auto-create; Django `loaddata` conversely does *raw* saves that skip auto-creation AND skip signals (no CablePaths, no clean() validation) — `dumpdata`/`loaddata` is the wrong primitive.
2. **Cables**: identified only by endpoints; endpoints are generic FKs. Serialize as `(device_key, component_type, component_name) ↔ (device_key, component_type, component_name)` + status/type/label. One-cable-per-endpoint uniqueness means idempotent replay must check-before-create. **Cross-site edges** — cables to CircuitTerminations or to devices outside the subtree — must be detected and flagged/skipped, not cloned. Front/rear port cabling requires rear ports (and their `positions` counts) to exist first.
3. **IPAM ordering & namespace**: IPs hard-fail without a parent Prefix in the namespace; primary_ip requires the interface assignment to exist (two-phase device write); the IPAddressToInterface role booleans are data that naive exports miss; /31-/32 and pool/container `type` semantics affect parenting.
4. **VLAN identity**: group-less VLANs have pk-only natural keys; exports must bind them to a group or synthetic ordinal.
5. **Modules (2.3+)**: component names derive from module-bay position templates (`{module}` placeholders); export must record the module tree by bay position and let name templates re-render, not copy literal names blindly.
6. **ConfigContexts**: rule-scoped and global. Role/platform/tag-scoped contexts apply to the new site automatically; **location-scoped ones silently won't** — the tool must either mutate shared ConfigContext.locations (side-effect on a shared object) or report the gap. Local context on Device is per-object JSON and copies cleanly.
7. **Location tree depth**: natural keys are variadic ancestor chains; instantiating a site under a different-depth parent or different LocationType chain breaks naive name-chain references. Export should store *relative* paths from the site root and require the target root's LocationType to match (LocationType is immutable per Location and its `content_types` must permit racks/devices/prefixes/VLANs).
8. **Status/Role/Tag content-type gating**: references resolve by name, but if replaying into another Nautobot instance the content_types m2m may not include the needed models — validate Tier 0 up front.
9. **Relationships & custom fields**: RelationshipAssociations are (content_type, pk) pairs on both ends — need natural-key resolution and an out-of-scope policy; custom select-field choices must exist; `_custom_field_data` copies as JSON.
10. **Design Builder-specific** (option b): open bugs [#184 import mode + connect_cable](https://github.com/nautobot/nautobot-app-design-builder/issues), #207 rack-position idempotency, #220 next_prefix idempotency; a fully-materialized YAML for a real site (dozens of devices × 50+ interfaces + IPs + cables) will be tens of thousands of YAML entries — generation is fine, human review/maintainability of the artifact is questionable, which undercuts the "designs as reviewable intent" value unless the generator emits a *parameterized Jinja design* rather than a flat dump. Design Builder's real differentiators are lifecycle: deployment tracking, ownership, decommission (with unlink-not-delete option since v2.1), and data protection.

## 6. Feasibility read (for the options analysis)

- Both options require the identical hard core: a site-graph **exporter** with natural-key serialization, component-vs-template diffing, synthetic cable/VLAN identity, and a **parameter mapper** (names, IP supernets, VLAN ids, namespace). Neither exists off the shelf.
- Option (a) export-JSON + instantiate-Job: full control of ordering (the 9-tier order in §2 is deterministic), no dependency on Design Builder's bug surface; loses lifecycle tracking unless built.
- Option (b) generate Design Builder YAML: the DB runtime already implements sequential creation, `!create_or_update` idempotency, `!ref` forward-handles, cable extension, and deployment lifecycle/decommission — genuinely useful — but inherits its open idempotency/cable-import bugs, its version-branch split (2.4-LTM vs 3.x), and produces enormous generated designs unless the generator emits Jinja-parameterized templates (harder). A hybrid (exporter produces an intermediate JSON; a thin backend renders either direct ORM calls or DB YAML) keeps the decision reversible.
