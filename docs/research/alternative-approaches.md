# alternative-approaches

## Summary
As of July 2026 the Nautobot platform picture is: core is on 3.1 (v3.1.0 2026-04-14, v3.1.7 2026-07-06; 3.0.0 shipped 2025-11-17; 2.4 is the LTM line), and nothing in core 2.x–3.1 provides "clone a site" or site-template/wizard functionality — the clone button remains a shallow single-object form pre-fill, and the equivalent NetBox feature request (#1994, 2018) was never implemented. So every option here is "build it as a Job"; the question is how much scaffolding you buy vs. build. Importantly, Design Builder is NOT abandonware — v3.1.1 shipped 2026-06-23 with Nautobot 3.0/3.1 support and active releases — so the hybrid option remains viable; the zero-adoption problem is an authoring-UX problem, not a maintenance problem.

The strongest low-effort path is Option 1 (plain "site factory" Job): it is literally the documented reference pattern in Nautobot's own Jobs developer guide ("Location Provisioning Job" / the classic "NewBranch" example), Jobs give you input forms (ObjectVar/StringVar/IntegerVar with dynamic query_params), and since Nautobot 2.0 you control atomicity yourself with @transaction.atomic (all-or-nothing rollback on failure is ~3 lines). Its weaknesses are exactly what the other options fix: the site topology lives in Python (every topology change is a code change), re-run safety is only as good as your get_or_create discipline, and there is no decommission story. Option 3 (SSoT/DiffSync with a "golden site" source adapter) buys idempotency, diffing, dry-run (diff preview), and re-run safety for free, and the ssot contrib module (NautobotModel/NautobotAdapter) auto-generates all Nautobot-side CRUD from declarative model definitions — but you still hand-model ~10-15 object types, and cables/generic-FK terminations plus device-component auto-creation from DeviceTypes are known friction points. Option 2 (JSON snapshot export + import job) is fully supported by platform primitives — GraphQL (read-only) or serializers for export, natural keys (natural_key()/get_by_natural_key(), 2.0+) for portable references, REST bulk-create (POST a list; all-or-none) — but the import side rapidly re-invents either Option 1's ORM code or Option 3's diffing; the netbox-importer's generic source-agnostic DiffSync generator proves the pattern but is an internal API you'd be vendoring.

Option 4 (generator that emits Design Builder YAML from an existing site) is the only option that yields per-object/per-attribute ownership tracking, dependency-aware decommissioning, and brownfield import (import_mode) without building that plumbing yourself — Design Builder's lifecycle feature is genuinely unique among these options and would cost weeks to replicate. The hybrid's risks: reverse-engineering faithful YAML (cables, custom fields, relationships) is the hard 30%, generated YAML still needs Jinja parameterization to be a reusable template (name/prefix substitution — mechanical, but device-count changes are not), and Design Builder has a documented history of severe performance problems at scale (issue #111: ~5,000 objects took 18h under atomic mode; fixed via PR #117, but deployment-mode tracking overhead at 1000+ objects deserves a spike). Recommended framing for the options doc: Option 1 for fastest time-to-value, Option 3 if idempotent re-runs/drift-correction matter, Option 4 only if lifecycle/decommission is a hard requirement — and note Options 1→4 can be staged (a well-factored "site spec" dict can later be rendered to Design Builder YAML instead of ORM calls).

# Alternatives to Design Builder for template-driven site generation in Nautobot (research as of 2026-07-12)

## Platform baseline (mid-2026)

- Nautobot core release train: **3.1 is current** (v3.1.0 released 2026-04-14; v3.1.7 on 2026-07-06). 3.0.0 shipped 2025-11-17; **2.4 (2025-01-10) is the LTM line**. Sources: [release notes index](https://docs.nautobot.com/projects/core/en/latest/release-notes/), [3.0 notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-3.0/), [3.1 notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-3.1/).
- **Nothing in core 2.x–3.1 changes the fundamental picture**: no site cloning, no site templates, no provisioning wizard. 3.1's relevant-but-minor additions: enhanced bulk rename (regex find/replace), bulk VLAN add/remove on interfaces, embedded modals for creating dependent objects inline, job forms restructuring (`Job.as_execution_form()`), job console logging. 3.0's relevant items: **Approval Workflows** (replaces `approval_required`; multi-stage sign-off attachable to job execution — free governance for any job-based option, but a breaking change to migrate), Data Validation Engine merged into core (your factory's output can be validated by core rules). 2.4 added JobQueues (Kubernetes execution), singleton jobs, `Job.fail()`.
- Nautobot's per-object "clone" (`clone_fields`) is only a **create-form pre-fill** — not a deep copy. The "clone an entire site" request has existed since NetBox days and was never implemented ([netbox#1994, 2018, closed unimplemented](https://github.com/netbox-community/netbox/issues/1994), [netbox#33](https://github.com/netbox-community/netbox/issues/33)); the ecosystem's standing answer is "write a custom script/job" ([NetBox Labs Zero-to-Hero 11](https://netboxlabs.com/zero-to-hero-11-custom-scripts/)).
- **Design Builder maintenance status** (relevant to whether hybrids are safe): actively maintained. v3.1.1 (2026-06-23, bugfix), v3.1.0 (2026-04-12, added `next_ip` action tag + deployment-membership UI panels), v3.0.0 (2025-11-17, Nautobot 3.0 + Py3.13), v2.3.0 (2025-12-09, LTM line for Nautobot >=2.4.20). Source: [releases](https://github.com/nautobot/nautobot-app-design-builder/releases). The observed zero adoption is an authoring-UX problem, not project abandonment.

## Option 1 — Plain Python "site factory" Job (ORM-direct)

**What it is.** A single Nautobot Job class taking minimal inputs and creating the full object graph via the Django ORM. This is the *officially documented pattern*: the current Jobs developer guide ships a "Location Provisioning Job" reference implementation (permission checks via `self.user.has_perm()`, batch creation via `validated_save()`, dependent dropdowns, CSV output) — [Job Patterns](https://docs.nautobot.com/projects/core/en/stable/development/jobs/job-patterns/) — descended from the classic v1 "NewBranch" example (`site_name`, `switch_count`, `switch_model` → creates site + access switches) — [v1 jobs docs](https://archive.docs.nautobot.com/projects/core/en/v1.4.1/additional-features/jobs/).

**Input forms.** Rich variable system, rendered automatically as a UI form and exposed via REST: `StringVar` (with `regex` validation — good for device-name patterns), `IntegerVar` (min/max — device counts), `ChoiceVar`, `BooleanVar`, `ObjectVar` (model-backed dropdown with `query_params` supporting dynamic dependent filtering, e.g. `{"manufacturer_id": "$manufacturer"}`), `MultiObjectVar`, `IPNetworkVar` (prefix seed), `FileVar`, `JSONVar`. Sources: [Jobs platform docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/platform-functionality/jobs/), [Job Structure](https://docs.nautobot.com/projects/core/en/stable/development/jobs/job-structure/).

**Atomicity / rollback-on-failure.** Since 2.0, Nautobot **no longer wraps `run()` in a transaction**; you opt in with `@transaction.atomic` on `run()` or a context manager — giving clean all-or-nothing behavior for a factory job in ~2 lines ([migration guide](https://docs.nautobot.com/projects/core/en/stable/development/jobs/migration/from-v1/)). Caveat learned from Design Builder's history: one giant transaction over thousands of objects is a DB-lock and performance hazard (see Option 4); for big sites, chunked transactions with compensating cleanup are safer.

**Dry-run.** `dryrun = DryRunVar()` sets `supports_dryrun` (and under the old system allowed approval bypass), but **the author implements the dry-run semantics** — typically `with transaction.atomic(): ...create everything...; if dryrun: raise` or log-only mode. `dryrun_default = True` in Meta available. Not free, but cheap if the job is transaction-wrapped.

**Assessment.**
- *Authoring/adoption effort:* **Lowest of all options** (roughly days to a first working factory for a fixed reference topology). One Python file loaded from a Git datasource; users see a normal Nautobot job form. No new frameworks for the team to learn beyond Django ORM.
- *Flexibility:* **Best-in-class** — arbitrary logic for naming patterns, counts, IP math (`netaddr`/`ipaddress`), conditional topology. This is precisely where Design Builder YAML is weakest.
- *Maintainability:* The topology is code. Every design change = Python change + review; risk of the job becoming a 2,000-line monolith. Mitigation used in the wild: keep the *data* (reference topology) in a YAML/JSON file loaded via `load_yaml()` (bundled-file support is documented) and keep the job as the engine — which is effectively building your own mini-Design-Builder, a slippery slope worth naming in the options doc.
- *Idempotency/re-run:* Not free. `get_or_create()`/`update_or_create()` discipline everywhere, plus uniqueness collisions (Device name+tenant+location constraints — see [nautobot#4499](https://github.com/nautobot/nautobot/issues/4499)) handled manually. Re-running to "fix drift" is out of scope unless you write diff logic (that's Option 3's job).
- *Rollback/decommission:* **None after commit.** Deleting a deployed site later means a second hand-written decommission job with correct dependency ordering, or manual bulk-delete. This is the biggest gap vs. Option 4.
- *Plumbing to build:* input validation, naming/IP generators, idempotency, decommission job, progress logging. All boring, all yours.
- *Real examples:* official docs' Location Provisioning Job (above); NTC blog series "Writing Your First Nautobot Job" pt.1–3 ([pt.3, 2025-07-10](https://networktocode.com/blog/writing-nautobot-job-part-3-implementation-guide-2025-07-10/)); community job collections ([housepbass/Nautobot-Jobs](https://github.com/housepbass/Nautobot-Jobs), [dpeachey/nautobot-custom-jobs](https://github.com/dpeachey/nautobot-custom-jobs)); NetBox-side "populate new devices and cables for a new site" custom-script tutorials.

## Option 2 — Export job (JSON snapshot) + import job (rebind + create)

**Export half.** Two viable mechanisms, both cheap:
- **GraphQL**: one nested query can pull a whole site (location → racks → devices → interfaces → IPs …) in a single request; saved GraphQL queries are first-class objects. But GraphQL is **strictly read-only — "support ... is limited to query, mutations are not supported"** ([GraphQL docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/platform-functionality/graphql/)) — so it's export-only. Watch for shape mismatch: GraphQL output ≠ REST write payloads; you'll transform.
- **Serializer/natural-key based**: iterate the object graph in a job and emit REST-serializer dicts, or use Django `dumpdata`-style serialization. Nautobot 2.0+ gives every `BaseModel` **natural-key APIs**: `instance.natural_key()`, `Model.objects.get_by_natural_key(...)`, `natural_key_field_lookups` ([uniquely-identifying-objects docs](https://docs.nautobot.com/projects/core/en/stable/development/apps/api/platform-features/uniquely-identify-objects/), [2.0 natural-keys dev docs](https://docs.nautobot.com/projects/core/en/v2.0.0-beta.2/development/natural-keys/)). Natural keys are exactly what makes a snapshot *rebindable*: refs stored as `["AMS01", "sw-01"]` instead of UUIDs, so the import job can substitute the new site name before resolution. Note: the 2.0 `composite_key` string form exists ([2.0 release](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.0/)) but has disappeared from current platform docs — treat it as deprecated and use natural-key tuples/nested attributes instead (medium confidence on formal deprecation status).

**Import half.** Platform primitives that help:
- **REST bulk create is supported**: "To create multiple instances ... make a POST request to the model's list endpoint with a list of JSON objects"; bulk PATCH/DELETE also supported and **all-or-none atomic per request**; related objects on write may be specified by **UUID, nested attributes, or natural key** ([REST API overview](https://docs.nautobot.com/projects/core/en/stable/user-guide/platform-functionality/rest-api/overview/)). An import job could equally use the ORM directly (faster, in-process) with `get_by_natural_key` for ref resolution.
- **The proven code pattern for "JSON dump → Nautobot" already exists**: nautobot-app-netbox-importer's importer is split into a **generic, source-agnostic layer** — `SourceAdapter` consumes any callable yielding `SourceRecord(content_type, data-dict)`; `NautobotAdapter` introspects the running Nautobot schema; `DiffSyncModel` classes are **generated dynamically** from the data + schema ([generator docs](https://docs.nautobot.com/projects/netbox-importer/en/latest/dev/generator/), [data flow](https://docs.nautobot.com/projects/netbox-importer/en/latest/dev/data_flow/)). A "Nautobot site snapshot" is structurally much closer to Nautobot than a NetBox dump, so this generic layer could theoretically ingest it with a thin source shim. **Risk:** it's an internal API of the netbox-importer app, not a supported standalone library — you'd be vendoring/pinning it.

**Assessment.**
- *Authoring/adoption effort:* Export job: ~days. Import job: **this is where the effort hides** — dependency ordering (LocationType→Location→RackGroup→Rack→DeviceType→Device→Interface→Cable→Prefix→VLAN→IP→primary_ip backpatch), rebinding rules (which names get rewritten vs. shared refs like Roles/Statuses/DeviceTypes that must already exist), and reconciling **auto-created device components** (creating a Device from a DeviceType auto-instantiates interface/port templates — [docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/feature-guides/getting-started/creating-devices/)); the import must match-and-update those, not create duplicates. Realistically 2–4x the export effort.
- *Flexibility:* Good for pure "stamp out a copy with new names/prefixes" (string/prefix substitution in the snapshot before load). **Poor for structural variation** — changing device counts or models means editing the JSON graph, which is worse UX than a job input.
- *Maintainability:* Snapshot format is yours to version. Nautobot upgrades can change serializer shapes; natural keys are stable-ish but admin-configurable (`DEVICE_NAME_AS_NATURAL_KEY`, `LOCATION_NAME_AS_NATURAL_KEY` settings exist).
- *Idempotency/re-run:* Not inherent. A naive importer double-creates or collides on re-run; making it idempotent = re-implementing DiffSync (at which point use Option 3).
- *Rollback:* Wrap import in `@transaction.atomic` for failure rollback; **no decommission tracking** post-commit (same gap as Option 1).
- *Real examples:* the netbox-importer itself (JSON dump → DiffSync → Nautobot) is the closest in-the-wild implementation of exactly this pipeline; no community "site snapshot clone" tool was found for Nautobot (absence itself is a data point — everyone writes bespoke jobs).

## Option 3 — nautobot-app-ssot + custom DiffSync source ("golden site template" as data source)

**What you get for free.** The [SSoT app](https://github.com/nautobot/nautobot-app-ssot) frames any sync as Source→Target with DiffSync: dashboard, sync history, per-object diff logs, **dry-run = diff-without-apply by design**, and idempotent convergence (re-run → no-op; drifted site → corrected back to template). The **contrib module** removes most of the code: subclass `nautobot_ssot.contrib.NautobotModel` (declare `_model`, `_modelname`, `_identifiers`, `_attributes` with type hints; **create/update/delete are provided**) and `contrib.NautobotAdapter` (declare model list + `top_level`; **load() is provided**), with FK references handled declaratively via double-underscore lookups (`location__name`, `status__name`). Sources: [Developing Jobs](https://docs.nautobot.com/projects/ssot/en/latest/dev/jobs/), [modeling docs](https://docs.nautobot.com/projects/ssot/en/latest/user/modeling/), [NTC contrib intro blog, 2025](https://networktocode.com/blog/2025-02-19-nautobot-ssot-contrib/), original how-to blogs ([basic](https://networktocode.com/blog/building-a-nautobot-ssot-app/), [advanced](https://networktocode.com/blog/advanced-ssot-app/)).

**Maintenance:** the healthiest app in this analysis — v4.5.2 (2026-07-06), v4.5.0 (2026-06-29), v4.4.0 (2026-06-01, thread-safe object caching), 12+ recent contributors, parallel v3.12.x LTM backports; v4.0+ loads source/target adapters in parallel (30–50%, up to 60% faster) ([releases](https://github.com/nautobot/nautobot-app-ssot/releases), [performance docs](https://docs.nautobot.com/projects/ssot/en/latest/user/performance/)).

**The custom part.** The source adapter — load the golden template (JSON exported from the reference site, or generated parametrically) into the same DiffSync models with target-site names substituted. Contrib explicitly does **not** help here ("only works with the Nautobot side"). You must model every object type in scope: Location, RackGroup, Rack, Device, Interface, Cable, Prefix, VLAN, IPAddress, IPAddressToInterface, plus refs to shared objects. Expect ~10–15 DiffSyncModel classes.

**Assessment.**
- *Authoring/adoption effort:* Medium — realistically 2–4x Option 1 for first delivery (framework learning curve + modeling), then flat. The contrib module cuts the historical SSoT boilerplate dramatically.
- *Flexibility:* Parameterization lives in the source adapter (Python), so it's as flexible as Option 1 for names/prefixes/counts; the SSoT job wrapper still exposes normal job variables for user input.
- *Maintainability:* Declarative models are compact and survive Nautobot upgrades well (NTC maintains contrib against core changes). Adding a new object type = one model class + adapter registration.
- *Idempotency/re-run:* **The headline win.** Free convergence, drift detection/correction, safe re-runs, and dry-run diff previews.
- *Rollback/decommission:* Partial. DiffSync can *delete objects missing from source* (dangerous — must scope the Nautobot adapter's load() strictly to the target site or it will try to delete the rest of your database; this scoping is a classic SSoT foot-gun). True decommission = sync against an empty source for that site — plausible but needs careful design; no attribute-level revert like Design Builder.
- *Known hard spots:* **cables** (generic-FK terminations don't fit contrib's declarative FK pattern — the netbox-importer needed special handling; some SSoT integrations skip cables); ordering (`top_level` + child ordering matters); device-component auto-creation reconciliation (same gotcha as Option 2); memory/query volume at scale ([performance docs](https://docs.nautobot.com/projects/ssot/en/latest/user/performance/): use `select_related`, one big query vs 7,000 small ones; profiling built in since Nautobot 1.5.17).
- *Real examples:* dozens of shipping integrations in nautobot-app-ssot (ServiceNow, Infoblox, ACI, DNA Center, Device42 — the [Device42 integration](https://github.com/nautobot/nautobot-plugin-ssot-device42) syncs full DCIM graphs including racks/devices/connections, proving the model coverage is achievable). No found example of a "template/golden-site" *file* as SSoT source, but the netbox-importer is precisely a file-sourced DiffSync import.

## Option 4 — Hybrid: generate Design Builder YAML from an existing site (humans never write YAML)

**Concept.** A one-time (or occasional) "reverse-engineer" job walks the reference site and emits a Design Builder design (YAML + Jinja variables + a small DesignJob class); Design Builder executes it, giving its lifecycle machinery. **No such generator exists anywhere today** — searched the repo, docs, and issues; Design Builder is strictly forward-direction. The nearest feature is deployment **import mode** (adopt existing unowned objects into a deployment's ownership records), which solves "bring our reference site under design management" but emits no YAML ([lifecycle docs](https://docs.nautobot.com/projects/design-builder/en/latest/user/design_lifecycle/)).

**Why bother:** Design Builder's deployment mode is the only thing in this analysis that provides, out of the box: per-object **and per-attribute ownership tracking**; **decommissioning** that deletes created objects and *reverts modified attributes*; **cross-design dependency protection** (can't decommission A while B depends on it); re-run/update of a deployment with change tracking. Replicating this on Options 1–3 is weeks of work (Design Builder itself took [issue #56](https://github.com/nautobot/nautobot-app-design-builder/issues/56) and a journal-model redesign to get there). See also [NTC design-driven NSoT blog, 2025-01-24](https://networktocode.com/blog/2025-01-24-design-driven-nsot/).

**Assessment.**
- *Authoring/adoption effort:* **Highest.** The generator must serialize the object graph into Design Builder's specific YAML dialect (`!ref`/`!create_or_update` action tags, ordering, model-key conventions) and then *parameterize* it — pure mechanical name/prefix Jinja substitution is scriptable; structural parameterization (variable switch counts) means generating Jinja loops, which is generator-of-templates territory and genuinely hard. Estimate: the generator alone ≥ the whole of Option 1, plus fidelity testing (export site → deploy design → diff against original; the diff harness is itself Option 2's export code). Cables, custom fields, relationships, and config contexts are the fidelity risks.
- *Flexibility:* After generation, parameters are whatever Jinja variables the generator threaded through — likely just site name/prefix seed initially. Worse than Options 1/3 for structural variation.
- *Maintainability:* Two artifacts to maintain (generator + generated designs) atop a third-party app. Design Builder is actively maintained (v3.1.1 2026-06-23) with an LTM line, so platform risk is moderate, but you're coupled to its YAML dialect across its major versions (1.x→2.x→3.x in three years).
- *Idempotency/re-run:* Good — designs use `!create_or_update` semantics and deployments can be re-run/updated with tracked changes; documented constraints: identifiers must be consistent across runs and object-list order must be stable.
- *Rollback/decommission:* **Best of all options** (see above).
- *Performance risk:* [issue #111](https://github.com/nautobot/nautobot-app-design-builder/issues/111) (Feb 2024): ~5,000 objects took **18 hours** (6+ hours on CPU-optimized hardware) under the atomic-transaction implementation; closed via PR #117 (non-atomic v2 job class). Current v3.1 deployment-mode overhead at 1,000+ objects is unverified — spike before committing.
- *Real examples:* [demo-designs](https://github.com/nautobot/demo-designs) (official example designs incl. new-site style designs, loadable as a Git datasource) and a 2025 community workshop series ([byrnbaker part 3.1](https://blog.byrnbaker.me/posts/Nautobot-Workshop-part3.1/)) show hand-authored full-site designs work; nobody has published a generator.
- *Lighter sub-variant worth listing:* skip YAML generation entirely — deploy sites with Option 1/2/3 and use Design Builder **import mode** afterward purely for ownership/decommission bookkeeping. Untested combination, but it decouples "creation logic" from "lifecycle tracking" and may capture most of the lifecycle value at a fraction of the cost.

## Option 5 — Anything new in core that changes the picture: **No.**

Checked 2.0→3.1 release notes ([2.0](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.0/), [2.4](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.4/), [3.0](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-3.0/), [3.1](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-3.1/)). No cloning, no site templates, no provisioning wizard. Genuinely relevant core items: natural keys + REST natural-key/nested-attribute writes (2.0) benefiting Option 2; bulk REST create/update/delete (all-or-none); Approval Workflows (3.0) gating any job; JobQueues/K8s execution + singleton jobs (2.4); Jinja2 rendering endpoint (2.4, handy for template debugging in Option 4); job console logging + bulk rename/bulk VLAN ops (3.1, minor). The Welcome Wizard app only imports device types; the Floor Plan app is visualization — neither addresses this problem.

## Comparative bottom line for the options doc

| | Effort to v1 | Flexibility | Idempotent re-run | Decommission | Plumbing you own |
|---|---|---|---|---|---|
| 1. Factory job | **Days–1wk** | **High** | DIY | None | Most |
| 2. Snapshot export+import | 1–3wk (import is the cost) | Medium (substitution only) | DIY | None | Much |
| 3. SSoT/DiffSync golden source | 2–4wk | High | **Free** | Partial/risky | Medium |
| 4. YAML generator + Design Builder | 4wk+ | Low–Medium | Good | **Best** | Least at runtime, most at build time |

Staging note: these compose. A factory job whose topology is a data structure (Option 1 done well) can later swap its ORM backend for a DiffSync adapter (→3) or a YAML emitter (→4) without changing the user-facing job. Recommend deciding primarily on two axes: **is decommission a hard requirement** (only 4 — or 4's import-mode sub-variant — delivers it cheaply) and **is drift-correction/re-run a requirement** (3 delivers it free).

## Open questions
- What is the actual object count of a representative site (devices x interfaces x IPs x cables)? This single number decides whether Design Builder's per-object overhead (issue #111 history) and SSoT's memory profile are irrelevant or disqualifying — a 30-device branch is fine everywhere; a 500-device campus needs a performance spike on options 3 and 4.
- Is decommission/rollback-after-deployment a hard requirement or nice-to-have? It is the ONLY differentiator that justifies option 4's extra complexity; if sites are never torn down programmatically, Design Builder's lifecycle value collapses and option 1 or 3 wins.
- Are cables and rack/position assignments in scope for the clone? Cable terminations are generic FKs and the hardest thing to model in every option (DiffSync, snapshot rebinding, and Design Builder YAML alike); explicitly descoping them changes effort estimates materially.
- Which Nautobot line is the org on — 2.4 LTM or 3.x? App version pinning differs (Design Builder 2.3.x vs 3.1.x; SSoT 3.12.x vs 4.5.x), and 3.0's Approval Workflows change how job execution gets gated.
- How much topology variation exists between target sites (fixed reference design with name/prefix substitution vs. variable device counts/models)? Pure parameter substitution favors options 2/4; structural variation (N access switches) favors options 1/3 where logic is code.
- Design Builder v3.1.x deployment-mode performance at ~1,000+ tracked objects is unverified — the atomic-transaction fix (PR #117) predates the current lifecycle ownership tracking; a 1-2 day spike deploying a full-size design is needed before committing to option 4.
- Does the netbox-importer generic generator have any roadmap to be extracted as a supported standalone library (worth a GitHub discussion/issue query to NTC), or would option 2's DiffSync variant require vendoring internal code?
