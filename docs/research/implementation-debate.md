# POSITION A-custom-job

THESIS: Build one plain Nautobot Job per deployment tier (S/M/L), creating the standard site directly via the Django ORM — no Design Builder, no SSoT, no intermediate spec as system of record. The standard is authored and documented, so the code IS the template; AI-assisted editing plus a retained read-only round-trip verifier makes maintenance cheap and safe. Every framework under debate was justified by problems (capture of an organic site, YAML-authoring pain, lifecycle) that Phase 0 answers and the new premises have dissolved — what remains of Design Builder, under the locked plan's own constraints, is an ORM adapter with extra steps, a bug surface, and an unverified identifier scheme.

KILLER FACT: The locked strategy's own plan concedes that v1 runs Design Builder in classic mode, where ChangeSets do not exist and the provisioned_from custom-field stamp 'is the only record of what a deployment created' (capture-to-design-plan.md §3.3) — the exact audit mechanism Option A uses — while identity.py's shipped floor policy downgrades unsafe lookups to plain !create, forfeiting idempotency, because single-field identifier lookups can 'silently match — and mutate — another site's' objects (identity.py, 'the worst failure mode in the whole design'). Lifecycle waived and idempotency downgraded, Design Builder's remaining contribution is sequential object creation — which the Django ORM does natively, without the ~1,450 LOC of escaping/identity/codegen written to appease it, without five in-code SPIKE-TODOs, and without a High-rated unverified identifier scheme standing between the org and its first deployed site.
