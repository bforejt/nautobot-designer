# design-builder-capabilities

## Summary
Design Builder (nautobot-app-design-builder) is an actively maintained NTC/Nautobot app (v3.1.1, June 23 2026) whose core is a generic ORM-materialization engine: a design is just a Python dict/YAML mapping of model-verbose-plural-names to object attribute maps, with "action tags" (quoted string keys like "!create_or_update:name", value strings like "!ref:foo") that control get/create/update semantics, cross-object references, and pluggable custom behaviors. Design files are Jinja2 templates rendered against a Context (populated from Nautobot Job input vars plus optional YAML context files and Python methods) and then parsed with plain yaml.safe_load — which means pure JSON design files work today with no code changes, because YAML action tags are ordinary quoted string keys/values, not YAML-native tags. Critically for the proposed tooling, the engine (nautobot_design_builder.design.Environment.implement_design(design_dict, commit=True)) is directly callable from any Job or management command with a plain dict — no Jinja, no DesignJob subclass required — so a "site exporter Job + instantiate-from-JSON Job" could reuse Design Builder's dependency-resolution/validation machinery without authoring any YAML by hand.

The differentiators over a plain Job are the lifecycle features (design_mode="deployment"): named Deployments per design, ChangeSet/ChangeRecord tracking of every created/updated object and attribute, re-run/update semantics (objects absent from the new run get decommissioned), full decommission/rollback of a deployment, an import mode that claims ownership of pre-existing (brownfield) objects, and opt-in data protection preventing out-of-band edits/deletes of design-owned objects. These features work but carry real maturity caveats: docs contain TODOs admitting update only works when every object uses identifier action tags; open bugs include non-idempotent rack positions (#207) and next_prefix (#220), import mode broken with the connect_cable extension (#184), decommission edge cases (#165, #166), and error-reporting problems (#232, #286). Ordering is partly manual: top-level model keys execute in document order, nested children and deferred FK saves are handled automatically, but !ref references are backward-only (must be defined before use) and cross-file ordering follows the design_files list.

Maintenance/compatibility is a decision-critical fork: Design Builder 3.x (3.0.0 Nov 2025, 3.1.0 Apr 2026, 3.1.1 Jun 2026) requires Nautobot >=3.0,<4.0; Nautobot 2.x users are pinned to the ltm-2.4 branch at v2.3.0 (Dec 2025, nautobot >=2.4.20,<3.0), which per NTC's stated policy gets critical bug/security fixes only. The project is alive (57 commits on develop in H1 2026, ~16 releases, 24 open issues) but has tiny community traction (15 stars, 10 forks), consistent with the zero-adoption problem observed internally. Designs are packaged as standard Nautobot Jobs (a `jobs` package, locally via JOBS_ROOT or via a Git repository data source, e.g. the nautobot/demo-designs repo), and an extensions API (AttributeExtension/ValueExtension with a `tag` name, registered per-job via Meta.extensions) makes it straightforward to add custom action tags that could simplify authoring or support an exporter/importer workflow.

## 1. Design YAML format and data flow

A design file is a **Jinja2 template that renders to YAML** (`docs/user/design_development.md`). The rendered document is a mapping whose **top-level keys are model verbose plural names** (`devices` → dcim.Device, `locations` → dcim.Location; the map is built dynamically from every installed app's models in `Environment.__init__`, so plugin models work too). Each value is a list (or single dict) of attribute maps.

Key syntax elements:
- **Query fields** `field__relatedfield: value` — expands to an ORM `.get()` on the related model (`platform__name: "Arista EOS"` → `Platform.objects.get(name=...)`). Dict values allow multi-criteria lookups.
- **Nested relationships** — children lists (e.g. `interfaces:` under a device, `children:` under a location) are auto-associated with the parent; FK/M2M save ordering is handled by the `ModelInstance` proxy layer (`design.py`).
- **Action tags as keys** (must be quoted in YAML): `"!create_or_update:<field>"`, `"!update:<field>"`, `"!get:<field>"`, `"!ref": name`, `"!git_context": {destination, data}`, plus contrib tags (`!connect_cable`, `!next_prefix`, `!child_prefix`, `!bgp_peering`, `!next_ip`, `!lookup`). Implementation: `ModelMetadata.attributes` setter (design.py ~line 251) — any key starting with `!` is split on `:`; if the first token matches a registered AttributeExtension it's dispatched there, otherwise it's treated as an action (`get/create/update/create_or_update`) with the second token as the lookup field. The docs note `!update`/`!create_or_update` should only target unique fields; multiple matches raise an error.
- **Action tags as values**: any *string value* starting with `!` is resolved via ValueExtensions (`Environment.resolve_value`), chiefly `"!ref:<name>"` and `"!ref:<name>.<attribute>"` (dotted access returns an attribute of the referenced object).
- **`custom_fields:`** dict is handled specially; **`model_metadata:`** dict supports `save_args`; a per-field **`{"deferred": true}`** flag postpones assignment until after dependent saves (canonical example: `primary_ip4` referencing an IP created on the device's own interface).
- **`design_mode`** in Job Meta: `classic` (ad-hoc, no lifecycle tracking) vs `deployment` (full lifecycle).

**Variable/data flow (Job → Context → Template):**
1. `DesignJob` (subclass of Nautobot `Job`, `design_job.py`) declares normal Job vars (StringVar, ObjectVar, IPNetworkVar…). Deployment-mode jobs auto-add `deployment_name` and `import_mode` fields (`_get_vars`).
2. Meta.`context_class` points to a `nautobot_design_builder.Context` subclass; job input dict is passed to its constructor and becomes instance attributes.
3. `@context_file("context.yaml")` decorator merges YAML files into the context; **values inside context YAML may themselves be Jinja templates** (lazy-rendered on lookup, e.g. `core_1_loopback: "{{ site_prefix | network_offset('0.0.0.1/32') }}"`). Context classes can add computed methods (e.g. external CMDB lookups) callable from templates.
4. `validate_*` methods on the context run before implementation (also wired into the job form's `clean`, so validation happens at form-submit time too) and raise `DesignValidationError` to abort.
5. `DesignJob.render()` builds a Jinja `Environment` (`jinja2.py`) with `StrictUndefined`, `trim_blocks/lstrip_blocks`, all Nautobot-registered Jinja filters (includes netutils), a custom resolver that falls back to the design context for unknown variables, and a `FileSystemLoader` whose search paths are the directories of the job class's full MRO — so `{% include %}` and `design_file` paths resolve relative to the job module.
6. Rendered text → `yaml.safe_load` → `Environment.implement_design(design, commit=not dryrun)` inside a DB transaction with savepoint rollback on error or dry-run. Rendered design files are attached to the JobResult as FileProxy artifacts.

## 2. JSON instead of YAML — YES (decision-critical)

Confirmed in code, not just YAML-superset theory:
- Parsing is `yaml.safe_load(self.rendered)` (`design_job.py:188`); PyYAML parses JSON documents.
- **Action tags are plain quoted string keys/values** — verified in shipped test designs (`tests/testdata/complex_design1.yaml` uses `"!create_or_update:name": "spine1"`, `"!ref:ethernet11"` as list values). The docs explicitly say keys beginning with `!` *must be quoted*. Since they're ordinary strings, they are fully representable in JSON: `{"devices": [{"!create_or_update:name": "sw1", ...}]}`.
- The design file passes through Jinja first, but a JSON file with no `{{ }}`/`{% %}` is a no-op template. No file-extension validation exists on `Meta.design_file` input (only output artifact names are forced to `.yaml`, cosmetic).
- Even simpler: skip files entirely. `Environment.implement_design()` accepts a Python dict, and the app ships `nautobot-server build_design <file>` (management command) that does `yaml.safe_load(file)` → `implement_design`. A generator Job that builds the design dict in memory (e.g. from an exported site) can call the engine directly.

Implication for the options analysis: option (b) "reverse-engineer a site into Design Builder YAML" is mechanically just "produce a dict and serialize it" — and option (a)'s JSON instantiator could still ride on Design Builder's engine for ORM resolution, ordering, validation, and (if desired) lifecycle tracking.

## 3. Ordering / dependencies

- **Top-level model keys run in document order** (`implement_design` iterates `design.items()`; Python/PyYAML preserve insertion order). The author must sequence model types manually (manufacturers before device_types before devices, etc.). Unknown keys raise `DesignImplementationError("Unknown model key ...")`.
- **Within an object**, the `ModelInstance` proxy defers saves so FK/M2M targets are saved first; nested children are created after the parent; `deferred: true` handles the remaining cycles (device→interface→IP→device.primary_ip4).
- **`!ref` is backward-only**: `ReferenceExtension.value` raises `DesignImplementationError("No ref named X has been saved in the design.")` for forward references. No topological sort of the document exists.
- **Multiple design files** (`Meta.design_files`) run sequentially sharing one Environment/context, so refs created in file 1 are usable in file 2. Caveat in a code TODO (design.py ~line 796): commit is per-design-file, so with multiple files a later failure does not un-commit extension side effects of earlier files.
- Nested lookups in `!create_or_update` query filters (double-underscore params) are recursively resolved as `!get` child objects.

## 4. Extensions API (custom action tags)

`ext.py`: subclass `Extension` via `AttributeExtension` (key-position tags) and/or `ValueExtension` (value-position tags); provide class attr `tag = "mytag"`; implement `attribute(self, *args, value, model_instance)` (args = extra `:`-delimited tokens from the key; may return a `(key, value)` tuple or dict merged back into the object's attributes) or `value(self, key)`. Optional `commit()` / `roll_back()` hooks fire after successful implementation / on failure (used by git_context to push/clean up repo files). Extensions are per-Environment singletons, registered via `Meta.extensions = [MyExtension]` on the design job. Contrib examples (`contrib/ext.py`) show the pattern is powerful: `!connect_cable` (creates cable + terminations from a `to:` query), `!next_prefix` (allocates next available prefix from parent pools, with `identified_by` for idempotency), `!child_prefix`, `!bgp_peering` (requires BGP models app), `!next_ip` (3.1.0). Writing tags like `!site_from_template` or bulk-expansion helpers to simplify authoring is squarely within the intended use of this API and requires no upstream changes.

## 5. Lifecycle features (the value-add) and maturity

Models (`models.py`):
- **Design** — 1:1 with a Nautobot Job whose class descends from DesignJob (auto-created by signals); carries version/description/docs from Meta.
- **Deployment** ("Design Instance") — named instance per (design, deployment_name); statuses Active/Disabled/Decommissioned; deletion blocked unless Decommissioned.
- **ChangeSet** — one per job run of a deployment (1:1 with JobResult); **ChangeRecord** — one per touched object, storing per-attribute old/new values, `full_control` (True if the design created the object), ordered `index` for reverse-order revert.
- **Update/re-run**: re-running with the same deployment name creates a new ChangeSet; objects present in the previous ChangeSet but missing from the new one are auto-decommissioned (`previous_change_set - change_set` diff in `_run_in_transaction`). Docs list hard assumptions: identifier tags must be used consistently, identifiers can't change between runs, list expansion must preserve order. A docs TODO admits update "features are not working as expected" without identifier keys on every object.
- **Decommission**: reverts ChangeSets newest-first; full_control objects are deleted (blocked if other active designs reference them — cross-design dependency check), partially-owned objects get attribute-level rollback (including dict/JSON key-level revert for config contexts); a no-delete mode just unlinks tracking. Decommissioned deployments remain visible for history and can then be deleted.
- **Import mode** (brownfield): flag on deployment-mode runs; `create_or_update`/`update` actions claim existing objects — full_control if no other deployment owns them, attribute-level claims otherwise; conflicting attribute ownership across deployments raises an error. This is the closest existing feature to "adopt an existing site as a design deployment."
- **Data protection** (`custom_validators.py`): opt-in per-model via `protected_models` config (default `[]`); pre_delete signal blocks deleting design-owned objects, CustomValidator blocks changing design-owned attributes; `protected_superuser_bypass` default True.

**Maturity/known problems** (open issues as of 2026-07): #207 rack-positioned devices not idempotent (re-run fails); #220 next_prefix not idempotent; #184 import mode incompatible with connect_cable (cables can't be imported — significant for a site template with cabling); #165/#164/#166 decommissioning changeset/UI/config-context issues; #232 DesignValidationError prevents JobResult save; #286 error rendering swallows underlying errors (IndexError); #274 proposal to revise data protection; #161 rollback-to-previous-ChangeSet not implemented; #150 deployments can't migrate across design versions yet (versioning is "future"). ChangeSet docstring itself: idempotence pending "an identifier strategy for every object." Net: classic-mode creation is solid; deployment lifecycle works for the demo-style happy path but update/import around cables, racks, and prefix allocation — exactly the object types in a full-site template — has open defects.

## 7. Packaging / loading designs

- Designs are **standard Nautobot Jobs**: top-level `jobs` Python package; DesignJob subclasses registered with `register_jobs`; design templates + context YAML live alongside the job module (paths resolve relative to the job class file, including through inheritance via MRO search paths).
- Loaded **locally (JOBS_ROOT)** or via a **Git repository data source** — the standard Nautobot jobs-from-git mechanism; reference layout is github.com/nautobot/demo-designs (per-design packages: `context/` + `designs/0001_design.yaml.j2`). An `install_demo_designs` management command creates the git data source.
- `build_design` management command loads fully-rendered (non-template) design YAML directly into the DB — intended for sample data but demonstrates the template-free path.
- Job Meta specifics: `design_file` or ordered `design_files`, optional `context_class`, `extensions`, `report` (Jinja→markdown post-run report), `version`, `docs`, `design_mode`, optional `deployment_name_field`.

## Implications for the two proposed options
- **Option (a) (export site → JSON → instantiate Job)**: can be built *on top of* Design Builder's Environment without any YAML/Jinja authoring — the instantiate Job feeds a dict to `implement_design()` and optionally gains dry-run, validation, and (deployment mode) lifecycle tracking for free. The hard part Design Builder does NOT provide is the **exporter** (serializing an existing site into design-dict form, choosing identifiers, parameterizing names/prefixes) — nothing in the app or issues suggests such a reverse-engineering feature exists or is planned.
- **Option (b) (reverse-engineer to Design Builder YAML)**: format is machine-writable (plain dicts, quoted-string action tags, JSON-compatible); the generator must (1) order top-level model keys dependency-first, (2) emit `!create_or_update:<unique-field>` identifiers on every object if lifecycle/update is wanted, (3) use `!ref`/`!connect_cable` for cables — noting import-mode cable bug #184 if brownfield adoption is desired, and (4) inject Jinja placeholders only where user input should vary (or generate the document per-run and skip Jinja entirely).
- **Version gate**: if the Nautobot instance is 2.x, only Design Builder 2.3.0 (maintenance-only) is available; full current functionality requires Nautobot 3.x. This should be weighed before committing to the framework.

## Open questions
- Which exact Nautobot version is the target instance running? Design Builder 3.x requires Nautobot >=3.0; a 2.4 LTM instance is limited to the maintenance-only v2.3.0 (ltm-2.4 branch), which lacks 3.1 features and possibly the #258 code-injection fix (backport status unverified).
- Does the export use case include cables? Import mode is known-broken with the connect_cable extension (#184), and greenfield cable creation relies on !ref ordering or !connect_cable — this materially affects whether deployment/import mode can adopt an existing fully-cabled site.
- How reliable is deployment update/re-run for full-site-scale designs in practice? Open idempotency bugs (#207 rack positions, #220 next_prefix) and the docs' own identifier-key caveats suggest testing a representative site round-trip before committing to lifecycle features.
- Is there prior art for a site exporter? No issue/PR in the repo proposes exporting existing Nautobot data into design format — worth a quick search of NTC blog posts and the demo-designs repo history before building one (not found in this pass, but not exhaustively ruled out).
- If designs are generated programmatically per-run (dict in memory), do we want ChangeSet/Deployment tracking (requires design_mode='deployment' and a DesignJob) or is classic ad-hoc creation sufficient? This determines whether the DesignJob subclass and its Meta/packaging conventions must be adopted at all.
