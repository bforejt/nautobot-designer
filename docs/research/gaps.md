# Gap check (final)

## Missing considerations
- Root cause of the zero-adoption problem was never validated. The entire analysis assumes adoption failed because YAML authoring is hard, but nobody has interviewed the intended users or checked whether the real blocker was lack of process integration, training, mandate, or an actual recurring need to stamp out sites. If the root cause is organizational, an exporter tool will see the same zero adoption. A 1-week user-research step (who provisions sites, how often, what inputs they naturally have) should precede any build.
- How 'minimal user input' is actually collected is unexamined. Nautobot Job forms are flat and statically declared per Job class (StringVar/ObjectVar/IntegerVar/JSONVar/FileVar) — no wizard, no repeating groups, no per-template dynamic schemas. The realistic choices are: (a) one generated Job class per template (which is exactly Design Builder's packaging model — an argument FOR option b that nobody made), (b) a single generic instantiate Job taking a FileVar/JSONVar blob (poor UX, likely re-creates the adoption problem), or (c) a custom Nautobot App UI view/wizard (an entirely unconsidered option with meaningfully higher effort but the best UX). The options doc must pick a parameter-collection model explicitly.
- Unconsidered option: LLM-assisted design authoring. It is mid-2026; a cheap middle path is exporting a site snapshot (GraphQL/ORM) and using an LLM to draft/refactor Design Builder YAML or a site-factory Job, validated by dry-run/round-trip diff. This attacks the authoring-UX problem directly without building a full generic exporter, and degrades gracefully (human reviews the artifact in Git). Deserves at least a 1-2 day evaluation row in the matrix.
- Unconsidered option: provision from OUTSIDE Nautobot via pynautobot / the networktocode.nautobot Ansible collection (or REST bulk endpoints) with the template stored in Git. This gives code review, CI validation, diffing, and template versioning for free, and avoids Job runtime limits — at the cost of losing in-UI self-service. The analysis only considered in-Nautobot Jobs.
- Template lifecycle and governance is entirely missing: where exported templates live (Git repo with PR review vs. a Nautobot object vs. job attachment), who owns/approves template changes, and what happens when the 'golden site' is edited live after export (silent template drift). Related: snapshot/template SCHEMA versioning — a JSON snapshot or generated YAML produced under Nautobot 2.4 will not replay cleanly on 3.x (e.g., DEVICE_UNIQUENESS natural-key change, new required fields). Stored templates need a version stamp and a stated migration policy or they rot silently.
- Long-term maintenance ownership (bus factor) is unaddressed. A per-model exporter must track every Nautobot minor release that adds site-relevant models; nobody named an owning team, an update cadence, or the fallback if the owner leaves. This is the exact failure mode that killed Terraformer, applied internally. Also unconsidered: contributing the exporter upstream to the design-builder repo (or proposing it via an issue) to shift maintenance to NTC — nobody has even asked NTC/#nautobot Slack whether design generation is on their roadmap, risking building what the vendor ships next quarter.
- Testing strategy is absent. The natural core CI invariant is the round-trip property: export golden site -> instantiate into empty location -> re-export -> deep-diff equals empty (modulo parameterized fields). Needs representative-site fixtures (nautobot-server dumpdata is broken for Tags/GFKs per nautobot#3666, so fixtures must come from factories or the export tool itself), a two-line test matrix (2.4 LTM and 3.x), and explicit fidelity metrics (% of objects/attributes reproduced) as the acceptance bar for any option.
- Operational runtime constraints of Jobs were never analyzed: Nautobot's default Celery limits are 300s soft / 600s hard (SIGKILL). A full-site instantiate (10^3-10^4 objects, worse under Design Builder's per-object overhead) will exceed defaults — every option needs Meta soft_time_limit/time_limit overrides, probably a dedicated job queue/worker, and a decision on one giant @transaction.atomic (long-held Postgres locks on a live production SoT, SIGKILL mid-transaction) vs. phased commits with checkpoint/resume. Partial-failure UX (what the user sees and does after a failure at object 7,000 — resume, rollback, or manual cleanup) is undefined for options 1 and 2; only Design Builder's changeset gives rollback for free.
- Side-effect storm from bulk creation is uncovered: every created object fires change-log writes (ObjectChange table growth; default retention 90 days), webhooks, Job Hooks, and potentially SSoT/downstream integrations (ITSM tickets, monitoring, IPAM sync) — instantiating one site could emit thousands of webhook calls. Need a policy: suppress/batch notifications during instantiate, or warn downstream owners.
- Concurrency and re-entrancy: two users instantiating simultaneously (same or overlapping parameters) hit unique-constraint races mid-run. Nautobot 2.4+ core supports singleton jobs (is_singleton lock with _ignore_singleton_lock escape hatch) — an available mitigation nobody mentioned.
- Security/permission model for the new tooling: who may run an instantiate job (it is effectively arbitrary-object-creation-as-a-service); scoping the importer so a crafted snapshot cannot modify global/shared objects (Statuses, CustomFields, DeviceTypes) instead of only site-scoped ones; snapshot file provenance if FileVar upload is the input; Nautobot object-level permissions causing partial creation when the runner lacks rights to one model.
- Data-quality gate on the template site itself: a brownfield 'golden' site may contain orphan cables, devices without primary IPs, template drift, and inconsistent naming. The exporter needs a lint/validate pass with a human-reviewable report before a site is blessed as a template. Related existing tooling nobody mentioned: the Data Validation Engine (merged into Nautobot core as of 3.0; app v3.x line for 2.4) — its regex/min-max rules (a) will run against every object the clone creates and can fail a run mid-way if the template violates rules added later, and (b) are an existing mechanism for enforcing naming/numbering standards on cloned sites instead of building that into the tool.
- The site-data-model enumeration omits several core models added in 2.x that may be in a 'full site': SoftwareVersion/SoftwareImageFile (2.2, devices reference software_version), Controller and ControllerManagedDeviceGroup (2.2, wireless/SDN), InterfaceRedundancyGroup (HSRP/VRRP), DeviceRedundancyGroup, and the 2.4 Wireless models and Virtual Device Contexts. Each must be explicitly in- or out-of-scope; if source sites use controllers/wireless, the export graph and effort estimates change.
- Non-ORM artifacts are ignored: image attachments (rack/location/device images) are media files on disk, and config contexts/export templates sourced from Git repositories are not ORM rows — a clone silently drops them. Explicitly descope or handle.
- Where do users safely try this? No staging/sandbox strategy is discussed — first runs of an instantiate job against the production SoT is the realistic failure scenario. Options: a staging Nautobot instance, dry-run-first policy (DryRunVar), or instantiate-into-a-quarantine-Location pattern with promotion.
- No success metrics or pilot plan: define adoption criteria up front (time-to-provision a site vs. today, number of sites instantiated in first quarter, error/rollback rate), pick 2-3 pilot sites, and make the true acceptance test downstream: does Golden Config / intended-config generation render valid configs against a cloned site? Without this, 'zero adoption' cannot even be measured the second time.
- Which Nautobot line to target is treated as an open question but the decision pressure is missing: Nautobot 2.4 LTM bundles Django 4.2, which reached EOL in April 2026 (already past, as of July 2026), and NTC's LTM policy is critical/CVE fixes on a case-by-case basis with no fixed end date. New tooling should target 3.x from day one or make the platform upgrade an explicit project dependency — building against 2.4 LTM is building on a decaying target.

## Risks not covered
- UNPATCHED SECURITY VULNERABILITY ON THE 2.4 LINE: Design Builder issue #258 is a code-injection vulnerability (Jinja2 template injection via job input variables — e.g. a name input of '{% set x = mysite().devices.all().delete() %}' executes with ORM access). The fix (PR #259, merged 2026-02-12) first shipped in v3.1.0 (2026-04-12). There has been NO release on the ltm-2.4 branch after v2.3.0 (2025-12-09), so the only Design Builder version installable on Nautobot 2.4 is unpatched against a known injection flaw. If the org is on 2.4 LTM, any option that uses DesignJob carries this until NTC backports or the org upgrades — this converts the digest's 'backport status unverified' into a confirmed exposure.
- SECOND-ORDER JINJA INJECTION IN OPTION (b): DesignJob renders every design file through Jinja2 before yaml.safe_load. A machine-generated design embeds literal site data (descriptions, names, custom-field text) — any value containing '{{' or '{%' becomes executable template code with Nautobot ORM access in the render context. This is exactly the vulnerability class of #258, but introduced by the generator itself. The exporter must Jinja-escape/{% raw %}-wrap every literal, or the tool must bypass Jinja entirely by feeding dicts to Environment.implement_design (which also weakens the case for emitting YAML at all).
- ARTIFACT FORMAT LOCK-IN TO A LOW-TRACTION THIRD-PARTY APP: option (b)'s deliverable — a library of generated Design Builder YAML templates — is only executable while nautobot-app-design-builder exists and stays compatible. With 15 stars, one primary vendor, and a history of NTC sunsetting apps (version-control abandoned 2021, network-importer in maintenance, data-validation folded into core), deprecation is a live scenario; there is no stated contingency. Option (a)'s JSON + own instantiate Job has no such dependency. A mitigation nobody proposed: keep the intermediate 'site spec' JSON as the system of record and treat Design Builder YAML as a disposable render target.
- JOB RUNTIME DEATH BY DEFAULT CONFIG: Nautobot's default job limits (300s soft / 600s hard, then SIGKILL) will kill a full-site instantiate on any realistic site unless per-job time limits and worker/queue configuration are part of the delivery. A SIGKILL mid non-atomic run leaves a half-created site with no record of what was created (options 1/2) — safe cleanup after partial failure requires a creation journal, which is precisely the changeset capability only option 4 provides; options 1/2 must budget for building one or accept manual cleanup.
- DOWNSTREAM AUTOMATION STORM: thousands of object creations in one run fire webhooks, Job Hooks, and integration syncs at every downstream consumer (ITSM, monitoring, IPAM, network controllers). Nobody assessed whether downstream systems tolerate a burst of 10^3-10^4 change events, nor whether change-log/webhook suppression during instantiate is acceptable to auditors.
- VALIDATION-RULE COLLISION: data-validation rules (core in Nautobot 3.0+, or the DVE app on 2.4) and custom_validators from other installed apps run on every save; a template exported before a rule was added can fail instantiation halfway through with an opaque per-object ValidationError. The tool needs pre-flight validation of the rendered object set and clear surfacing of which rule failed — no option discussed this.
- REPEAT-ADOPTION RISK: all four options assume the tool itself was the adoption blocker. If site provisioning is infrequent (a few sites/year), no tool amortizes its build cost, and the honest recommendation may be Option 1 at its absolute minimum or nothing. The analysis lacks the base-rate question: how many site builds per year are actually expected?
- TEMPLATE/SNAPSHOT SCHEMA ROT ACROSS UPGRADES: stored templates (JSON or generated YAML) are silently invalidated by Nautobot core upgrades (model/field changes between 2.4 and 3.x, e.g. device natural-key/uniqueness changes) and by Design Builder major versions. Without a schema-version stamp, a re-validation CI job, and a stated re-export-after-upgrade policy, the template library becomes a liability at the first platform upgrade — the analysis discusses picking a version line but not surviving the transition.
- NO VENDOR-COORDINATION STEP: nobody has asked NTC (GitHub discussion, #nautobot Slack, or their PS arm) whether design generation/export is on the Design Builder roadmap — the repo shows they already experimented with lower-friction input (Excel import branch). Building a months-long internal tool that the vendor ships natively would be the worst outcome; a one-hour inquiry is missing from every plan.

## Research conducted to fill gaps (July 2026)

### 1. Design Builder code-injection vulnerability (#258) — 2.4 LTM line is unpatched
- Issue [#258](https://github.com/nautobot/nautobot-app-design-builder/issues/258): `_TemplateNode` evaluates user job-input strings as Jinja2 templates with Nautobot ORM objects in context; example exploit given in the issue is injecting `{% set nothing = mysite().devices.all().delete() %}` into a name variable. Reported as affecting **all versions**.
- Fix: [PR #259](https://github.com/nautobot/nautobot-app-design-builder/pull/259) (merged **2026-02-12** into develop) disables template evaluation for user script variables while keeping it for context files/classes.
- Per the [releases page](https://github.com/nautobot/nautobot-app-design-builder/releases), the fix first shipped in **v3.1.0 (2026-04-12)** ("Fixed code injection vulnerability"); the **ltm-2.4 branch has had no release since v2.3.0 (2025-12-09)** — so the only Design Builder installable on Nautobot 2.4 today is unpatched. Decision impact: any DesignJob-based option on a 2.4 deployment inherits a known injection flaw; also demonstrates the exact injection class that a YAML **generator** could re-introduce via literal site data containing `{{`/`{%`.

### 2. Job runtime limits (operational constraint on every option)
Per [Nautobot settings docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/administration/configuration/settings/): `CELERY_TASK_SOFT_TIME_LIMIT` defaults to **300 s** and `CELERY_TASK_TIME_LIMIT` to **600 s** (hard limit, task killed with SIGKILL). A full-site instantiate job must override per-job time limits and likely needs a dedicated queue/worker. Also relevant: `CHANGELOG_RETENTION` defaults to **90 days**; bulk creation writes one ObjectChange row per object (table growth + webhook fan-out).

### 3. Nautobot 2.4 LTM lifecycle pressure
Per the [Security and Maintenance Policy](https://docs.nautobot.com/projects/core/en/stable/user-guide/administration/security/): LTM branches receive only data-loss/CVE fixes, compatible dependency security updates, and case-by-case fixes — no features or performance work. Nautobot 2.4 bundles **Django 4.2, which reached EOL in April 2026** (already past); Nautobot cannot guarantee patches for post-EOL Django vulnerabilities and handles them case-by-case "while the LTM series remains active" (no fixed end date). Net: new tooling should target the 3.x line or explicitly schedule the platform upgrade first.

### 4. Concurrency control exists in core
Nautobot 2.4+ supports **singleton jobs** (singleton lock preventing concurrent runs, with an `_ignore_singleton_lock` execution-time escape hatch) — see [extras/models/jobs.py](https://github.com/nautobot/nautobot/blob/develop/nautobot/extras/models/jobs.py) and [nautobot.apps.jobs reference](https://demo.nautobot.com/static/docs/code-reference/nautobot/apps/jobs.html). Directly usable to serialize instantiate runs.

### 5. Core models missing from the site-graph enumeration
Per [Nautobot 2.2 release notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.2/): **SoftwareVersion / SoftwareImageFile** are core dcim models (ported from the Device Lifecycle app; Devices/InventoryItems/VMs reference a SoftwareVersion), and **Controller / ControllerManagedDeviceGroup** model SDN/wireless controllers. Combined with InterfaceRedundancyGroup, DeviceRedundancyGroup, and 2.4's Wireless models + Virtual Device Contexts ([2.4 release notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.4/)), these are site-relevant core models the export scope must explicitly include or exclude.

### 6. Data Validation Engine — interaction and opportunity
Per the [app repo/docs](https://github.com/nautobot/nautobot-app-data-validation-engine) and [Nautobot 3.0 release notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-3.0/): data-validation functionality (regex/min-max/required/unique rules on any model) **moved into Nautobot core at 3.0.0**; the standalone app's 3.x line continues for Nautobot 2.4 in security/critical-fix mode. Two decision impacts: (a) validation rules execute on every object an instantiate job saves — a clone can fail mid-run on rules added after the template was exported, so pre-flight validation and clear error surfacing are required; (b) it is an existing, zero-build mechanism for enforcing site naming/numbering standards on cloned sites, reducing how much validation the new tool must own.

# First-pass gap check (ran against partial research; retained for its sourced findings)

## Missing considerations
- THE PARAMETERIZATION PROBLEM (biggest gap): an exported site is a concrete instance, not a template. Neither research area addresses how snapshot values get abstracted — which fields are user seeds (site name/code, address, ASN) vs derived (device names from naming convention, prefixes allocated from a parent supernet, VLAN IDs reused vs re-allocated) vs stripped (serials, asset tags, UUIDs, geo coords, install dates, custom-field operational data). This layer is the hard 60% of every option and is orthogonal to which engine (plain ORM, DiffSync, Design Builder) materializes objects. The analysis needs an explicit 'input contract': the exact per-site parameter list and the substitution/derivation rule for every exported field.
- STRUCTURAL VARIATION between sites: a cloned golden site has a fixed shape. If real sites vary (2 vs 8 access switches, 1 vs 3 IDFs, optional OOB router), a pure snapshot cannot express loops/conditionals — you either maintain multiple golden sites (S/M/L variants) or reintroduce templating logic (Jinja loops), which is exactly the Design Builder authoring burden the project is trying to escape. This can invalidate the core premise and must be answered first: how much do target sites actually vary?
- IP/prefix SEED ALLOCATION strategy: where do the new site's prefixes come from — typed in by the user, or auto-allocated from a regional supernet (Nautobot REST 'available-prefixes' endpoint, or Design Builder next_prefix/next_ip tags — noting next_prefix has open idempotency bug #220)? Also VLAN ID policy (identical IDs per site vs unique) and DNS/hostname derivation. Nobody specified this.
- UNIQUENESS/COLLISION semantics when stamping clones: Nautobot 2.x Namespaces require Prefix/IPAddress/VRF uniqueness within a Namespace — today a warning, documented to become an enforced constraint in a future release. Cloning IPAM verbatim into the global Namespace collides; decide per-site Namespaces vs re-addressing. Same question for VLAN (group+vid scoping), device name (tenant-scoped natural key), rack names.
- EVENT SIDE-EFFECTS design decision: verified in code that Nautobot 2.x job execution wraps run() in web_request_context (nautobot/extras/jobs.py line 170), so every object a job creates/deletes is change-logged AND fires matching webhooks and JobHookReceivers. Mass instantiation or decommission of a full site will blast downstream systems (ServiceNow, event-driven pipelines, dynamic-group re-evaluation). Need an explicit decision: let them fire, disable hooks during runs, or batch/suppress.
- JOB RUNTIME AND PARTIAL-FAILURE model: Nautobot's default hard time limit for jobs is 10 minutes (CELERY_TASK_SOFT_TIME_LIMIT / time_limit, overridable per-job Meta). No option analyzed: single @transaction.atomic (long lock hold, all-or-nothing loss on minute-9 failure) vs chunked commits with checkpoint/resume (leaves half-built sites on failure — who cleans up, can a run resume?). Worker restart mid-run behavior is unaddressed.
- EXPORT FIDELITY CONTRACT + acceptance test: scope beyond core DCIM/IPAM is unlisted — custom fields, custom Relationships (generic-FK associations), tags, notes, config contexts, dynamic groups, secrets group references, computed fields, and plugin-app models (e.g., nautobot-bgp-models if in use). Define what's in/out, and adopt a round-trip test as the acceptance criterion: export site A, instantiate A', machine-diff A vs A' (the SSoT diff engine or object-count comparison can do this).
- SNAPSHOT DURABILITY ACROSS NAUTOBOT UPGRADES: a stored JSON snapshot or generated Design Builder YAML is coupled to one Nautobot version's model/field names. The 2.4→3.0 migration will invalidate stored templates (e.g., Data Validation Engine models moved into core in 3.0). Need snapshot schema versioning, a re-export-after-upgrade policy, and a statement of which Nautobot versions each stored template supports. This applies to every option, not just Design Builder.
- TEMPLATE GOVERNANCE: the golden site is a live production site that keeps changing. When is a snapshot taken, where does it live (git repository data source?), who reviews/approves template changes, and how do you record which deployed sites were stamped from which template version? Without this, 'clone the golden site' quietly becomes 'clone whatever the golden site looks like today'.
- LIGHTWEIGHT OWNERSHIP/AUDIT MIDDLE GROUND: nobody evaluated simply tagging (or custom-fielding) every created object with a deployment identifier — the SSoT Bootstrap 'System of Record' pattern — as a cheap alternative to Design Builder ChangeSets for answering 'which objects came from stamping run X' and enabling scripted teardown, without adopting DB's lifecycle machinery.
- UNCONSIDERED OPTION — Ansible collection: networktocode.nautobot (v6.2.0 May 2025, 103 modules including cable, front_port, rear_port, device_bay, ip_address_to_interface; Nautobot 3.x supported since v6.0.0) gives idempotent create/update per object plus free dry-run via check_mode; a site becomes a reviewable vars file in git. Costs: runs outside the Nautobot UI (no Job form/RBAC/JobResult), per-object REST is slow at site scale, no decommission. Worth a row in the options matrix, especially if the team already runs Ansible.
- UNCONSIDERED OPTION (dismissible) — Terraform provider: nautobot/terraform-provider-nautobot would give plan/apply/destroy lifecycle for free, but it is v0.0.1-alpha (educational-origin, beta at best) — evaluate-and-dismiss with citation so reviewers know it was considered.
- UNCONSIDERED BROWNFIELD ALTERNATIVE — device-onboarding v4: 'Sync Network Data From Network' imports interfaces, IPs, VLANs, VRFs, and cables (IOS/NXOS/Junos via CDP/LLDP) from live devices. If new sites are physically built before SoT entry, populating from the network competes with (or complements) cloning from a template; the analysis assumes SoT-first provisioning without stating it.
- UI/INTAKE MECHANISM for 'minimal user input': Nautobot Job forms are static single-page forms — no repeatable rows or wizards. Realistic choices: chained ObjectVars with query_params + a JSONVar/FileVar (the common NTC pattern of uploading a site-build spreadsheet), a custom App view/multi-step wizard (significant extra dev), or headless invocation via the Jobs REST API from ServiceNow/ITSM intake. None was compared; this directly shapes perceived usability and thus adoption.
- MAINTENANCE OWNERSHIP & SKILLS: who owns this tool through Nautobot upgrades? A plain Job is vanilla Django ORM (lowest skill bar, easiest handoff); DiffSync/SSoT and Design Builder extensions require framework expertise with tiny communities. Also unasked: does the org have an NTC support contract that could fund Design Builder fixes (#207, #220, #184) instead of engineering around them? And the 2.4 LTM end-of-support date bounds how long the ltm-2.4 DB pin is viable.
- TESTING STRATEGY: none proposed. Should include unit tests with Nautobot's TransactionTestCase and factory data, a CI harness (nautobot-server test in the standard app cookiecutter), an ephemeral dev instance (nautobot-docker-compose) seeded with a copy of the golden site, and the export→instantiate→diff round-trip as the regression test.
- RBAC / APPROVAL / BLAST-RADIUS CONTROLS: who may run instantiate and especially decommission? Nautobot 3.0's multi-stage approval workflows can gate destructive jobs; object permissions constrain what the job user may touch; policy of 'dry-run required before commit'. Also enforce post-generation standards with data validation rules (core in Nautobot 3.0; app v3.4.x LTM for 2.4) so generated data meets naming/addressing standards regardless of which option wins.
- ADOPTION ROOT-CAUSE AND SUCCESS METRICS: the analysis assumes YAML authoring difficulty caused zero adoption, but this is unvalidated — it may be trust, training, process fit, or no perceived need, in which case no exporter fixes it. Define success metrics (time-to-provision a site, % of new sites stamped via tool, rework rate) and a pilot plan (one real upcoming site, side-by-side diff vs hand-built).
- MULTI-TENANCY: tenant assignment of cloned objects and tenant-scoped uniqueness (device natural key includes tenant) — one line of design, but silent wrong-tenant clones are painful to unwind.
- DATA-PROTECTION INTERACTION: if Design Builder deployment mode with protected_models is adopted, design-owned objects reject out-of-band edits — which will fight other writers (SSoT syncs, device-onboarding, engineers doing break-fix). The interplay between design ownership and every other write path into Nautobot was not analyzed.

## Risks not covered
- Webhook/JobHook storm: verified that job ORM writes run inside web_request_context (nautobot/extras/jobs.py line 170), so instantiating or decommissioning a full site fires per-object webhooks/job hooks to all matching subscribers and writes thousands of ObjectChange rows — potential downstream flooding (ITSM tickets, event-driven automation cascades) and changelog bloat.
- Default 10-minute hard job time limit kills a large site instantiation mid-run; without @transaction.atomic this strands a half-built site with no defined cleanup/resume path; with one big transaction you get long lock holds on hot tables (Device, Interface, IPAddress) and total loss of a near-complete run.
- IPAM collision on clone: duplicating prefixes/IPs/VRFs into the same Namespace is only a warning today but documented to become an enforced constraint in a future Nautobot release — a cloning tool that 'works' now can hard-fail after an upgrade, and duplicate-prefix warnings silently degrade IPAM data quality meanwhile.
- Concurrent instantiations racing on next-available-prefix/VLAN allocation (no locking strategy discussed; Design Builder's next_prefix additionally has open idempotency bug #220).
- Stored templates silently break on Nautobot upgrades: snapshot JSON / generated YAML is bound to a version's model schema; after 2.4→3.0 migrations, previously exported templates may fail or, worse, import subtly wrong. No versioning/migration plan exists for the template artifacts themselves.
- Golden-site drift: the template is a live site; edits between snapshot and instantiation produce uncontrolled divergence across stamped sites, and there is no proposed mechanism to know which sites came from which template state.
- Silent fidelity gaps: exports that miss custom Relationships, config contexts, dynamic-group memberships, or plugin-app models (BGP, etc.) produce clones that pass casual inspection but are operationally incomplete — the failure is invisible until an automation depending on that data misbehaves.
- Decommission blast radius: Design Builder decommission (or any scripted teardown) deletes owned objects; run against the wrong deployment it deletes a production site. No approval gating, confirmation UX, or recovery story was discussed for the destructive path.
- Sensitive data leakage: exported snapshots stored in git may carry sensitive custom-field values or location data; secrets are references in Nautobot (safe), but the export scope review and repo access controls were not considered.
- Design Builder data protection conflicting with other write paths (SSoT jobs, onboarding, manual break-fix), causing operational lockouts or teams disabling the feature — negating the lifecycle benefits that justified choosing DB.
- Organizational risk: root cause of zero adoption is unvalidated; a technically better tool can fail identically if the barrier was trust/process/training. No pilot, success metric, or user validation step is in the plan.
- Support-window risk: Nautobot 2.4 LTM (and DB ltm-2.4 v2.3.0, Ansible collection 2.4-LTM-only backward support) all have finite maintenance windows; committing tooling to the 2.4 track without a 3.0 migration date embeds an expiry nobody scheduled. Unverified backport of DB security fix #258 to ltm-2.4 remains open.

**1. Jobs DO fire webhooks/change-log automatically in Nautobot 2.x+ (verified in source).** `nautobot/extras/jobs.py` (develop branch) line 170: job execution wraps `run()` in `with web_request_context(user=self.user, context_detail=self.class_path, context=change_context)`. Per the [change-logging docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/platform-functionality/webhook/) this context is what enables change logging and webhook enqueueing for ORM writes — so every option built on Jobs mass-fires webhooks/JobHooks per created object. Related core issue [#3015](https://github.com/nautobot/nautobot/issues/3015) (multiple hooks per single change via M2M) can amplify this.

**2. Job time limits.** Default hard time limit for a job task is 10 minutes; `soft_time_limit`/`time_limit` overridable per-job in Meta, globally via `CELERY_TASK_SOFT_TIME_LIMIT`. Exceeding the soft limit raises `SoftTimeLimitExceeded` for cleanup; hard limit kills with no exception. Sources: [Nautobot jobs docs](https://archive.docs.nautobot.com/projects/core/en/v1.4.1/additional-features/jobs/), [optional settings](https://archive.docs.nautobot.com/projects/core/en/v1.2.6/configuration/optional-settings/), core issue [#697](https://github.com/nautobot/nautobot/issues/697) (cleanup on Celery time-limit exceeded). Also confirmed by the [jobs migration guide](https://docs.nautobot.com/projects/core/en/stable/development/jobs/migration/from-v1/): jobs no longer run in a single atomic transaction by default.

**3. Namespace uniqueness is warning-now, constraint-later.** [Namespace docs](https://docs.nautobot.com/projects/core/en/stable/user-guide/core-data-model/ipam/namespace/): within a Namespace all VRFs/Prefixes/IPs must be unique; creating duplicates currently yields a warning, "in a future Nautobot release this will be changed to an enforced data constraint." Direct consequence: verbatim IPAM cloning into the default Namespace is a time bomb.

**4. Missing Option 5 — Ansible collection is viable and complete for site objects.** [networktocode.nautobot](https://docs.nautobot.com/projects/ansible/en/latest/networktocode.nautobot/index.html) has 103 modules; verified the module index includes `cable`, `front_port`, `rear_port`, `device_bay`, `rack`, `location`, `prefix`, `vlan`, `ip_address`, `ip_address_to_interface`, `device`, `device_interface` (no separate cable_termination module — terminations are cable-module params). Latest release v6.2.0 (2025-05-04); v6.0.0 (2024-11-15) began official Nautobot 3.x support, with 2.x support limited to 2.4 LTM ([releases](https://github.com/nautobot/nautobot-ansible/releases)). Idempotent modules + `check_mode` = free dry run; trade-offs: outside Nautobot UI/RBAC/JobResult, per-object REST speed, no decommission lifecycle.

**5. Terraform provider — evaluate and dismiss.** [nautobot/terraform-provider-nautobot](https://github.com/nautobot/terraform-provider-nautobot) is v0.0.1-alpha (originated as an educational exercise by nleiva, moved under the nautobot org, still beta/alpha). Plan/apply/destroy lifecycle would map perfectly to this use case, but maturity rules it out; document as considered.

**6. Brownfield alternative — device-onboarding v4 'Sync Network Data'.** [Device Onboarding app](https://docs.nautobot.com/projects/device-onboarding/en/latest/user/app_use_cases/) v4 syncs interfaces, IPs, VLANs, VRFs from live devices, and cable sync via CDP/LLDP was added for Cisco IOS/NXOS and Juniper ([NTC blog](https://networktocode.com/blog/device-onboarding-4-0/), issue [#201](https://github.com/nautobot/nautobot-app-device-onboarding/issues/201)). Relevant if sites physically exist before they exist in the SoT — an unstated assumption in the current analysis.

**7. Data Validation Engine moved into Nautobot core in 3.0.** Per the [DVE docs](https://docs.nautobot.com/projects/data-validation/en/latest/) and [Nautobot 3.0 release notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-3.0/): the app's functionality is core in Nautobot 3.0; app v3.4.x continues for Nautobot 2.4 LTM (security/critical fixes only). Useful as a path-independent guardrail: regex/min-max/custom rules enforce naming and addressing standards on whatever the generator creates — and it is another example of the 2.4-vs-3.0 dependency fork every option must state.
