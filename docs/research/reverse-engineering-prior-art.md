# reverse-engineering-prior-art

## Summary
No prior art exists for reverse-engineering existing Nautobot objects into Design Builder YAML designs — not in the design-builder repo (no issues, PRs, or branches about export/generation from existing objects), not in the NTC ecosystem, and not in the community (GitHub/PyPI searches found no site-clone or design-generator app). The closest thing is Design Builder's "import mode" (issue #158, PR #195, shipped v2.1.0 Oct 2024): it lets a hand-written design ADOPT matching existing objects into a Design Deployment (brownfield onboarding), but the YAML must already exist — nothing generates it. Notably, import mode has a still-open bug (#184) where it does not work with the connect_cable extension, and open idempotency issues around rack positions (#207) and next_prefix (#220) — cables and rack placement being exactly what a site-clone needs. Design Builder itself is actively maintained (v3.0.0 Nov 2025 for Nautobot 3.0, v3.1.1 June 2026) but has very low community traction (15 stars), and NTC's 2025-era workshops still teach hand-authoring.

The most instructive prior art is negative. NetBox core rejected "Ability to clone entire sites" (#1994) in 2018, with Jeremy Stretch's reasoning that the blocker is not serialization but the renaming/renumbering policy (racks, devices, prefixes, VLANs, IPs all need new identities), concluding it is "much more practical to script out your own unique logic for replicating a site using either the REST API or local ORM" — which directly endorses the proposal's option (a) (site-specific export + instantiate Jobs) over a generic framework. Cross-ecosystem analogues reinforce this: Terraformer was archived March 2026; Terraform's native `-generate-config-out` remains experimental after 3 years and produces over-specific literal config requiring heavy refactoring; kubectl's get→apply pattern requires scrubbing server-populated fields (kubectl-neat exists solely for this); and no facts-to-playbook tool ever succeeded in Ansible because generated artifacts capture state, not intent. The universal failure modes: over-specific output (every attribute incl. defaults/server-set values), IDs-vs-natural-keys breakage on replay, inability to infer what should be parameterized vs. copied literally, dependency ordering for replay, and high per-schema maintenance cost leading to tool abandonment.

Two facts favor feasibility of a scoped Nautobot implementation: Design Builder YAML references objects by natural-key-style queries (name-based field lookups, `!ref` for cables — no UUIDs), so generating valid YAML from the ORM is mechanically possible; and Nautobot 2.0+ has natural-key support (`instance.natural_key()`, `get_by_natural_key()`) plus GraphQL for one-query site snapshots — though `dumpdata --natural-primary` is known-broken for Tags/GenericForeignKeys (nautobot#3666), so a full-fixture snapshot path has landmines. The evidence pattern suggests: a purpose-built export-site-to-JSON Job + parameterized instantiate Job (option a) matches what every ecosystem converged on for "clone this thing" (purpose-built scripts with an explicit renaming/renumbering policy), while generating Design Builder YAML (option b) buys the design lifecycle (update/decommission/import-mode adoption) at the cost of inheriting its open cable/idempotency bugs and the classic generated-IaC over-specificity problem.

# Prior Art: Reverse-Engineering Existing Objects into Templates/Designs

Research date: 2026-07-12. Primary sources: GitHub (nautobot org, netbox-community, netboxlabs, hashicorp, GoogleCloudPlatform), docs.nautobot.com, networktocode.com, PyPI.

## 1. nautobot-app-design-builder repo: no reverse-engineering prior art

Searched issues, PRs, branches, and GitHub Discussions of [nautobot/nautobot-app-design-builder](https://github.com/nautobot/nautobot-app-design-builder) for "export", "reverse", "generate design", "from existing", "clone", "drift". Results:

- **Nothing proposes generating/exporting a design from existing objects.** Zero hits for "export" in issues or PRs. The repo has no GitHub Discussions at all.
- **Closest feature — "import mode" (brownfield adoption, not generation):**
  - [Issue #158 "Allow import of existing data into a Design Deployment"](https://github.com/nautobot/nautobot-app-design-builder/issues/158) (chadell, May 2024): adopt existing objects "as if generated by Design Builder" so they can be updated/decommissioned via the design lifecycle. Interesting comment thread: itdependsnetworks initially challenged whether this differs from idempotent `get_or_create`; chadell clarified the point is *persisting ownership* of "get" objects into the deployment.
  - Implemented in [PR #195 "Import mode for design lifecycle"](https://github.com/nautobot/nautobot-app-design-builder/pull/195) (merged 2024-10-21, port of 1.6-branch PR #181), shipped v2.1.0 (2024-10-23).
  - Documented in [design_lifecycle docs](https://docs.nautobot.com/projects/design-builder/en/latest/user/design_lifecycle/): new objects created normally; existing unowned objects claimed with "full_control"; objects owned by other designs allow attribute-level claims (except identifiers); conflicting attribute ownership fails the import. Documented limitations: identifiers must be consistent across runs, list ordering is assumed stable, imported changes record identical old/new values ("we can't infer which was the previous value").
  - **Known gap:** [Issue #184 "Import mode doesn't work with connect_cable extension"](https://github.com/nautobot/nautobot-app-design-builder/issues/184) — open since Aug 2024, still open. Cables are central to a site clone.
  - The docs explicitly contain **no mention of exporting/generating designs from existing data** (confirmed via docs fetch).
- **Related open issues that matter for a site-clone design:** [#207 devices with rack positions are not idempotent](https://github.com/nautobot/nautobot-app-design-builder/issues/207) (open), [#220 make next_prefix idempotent](https://github.com/nautobot/nautobot-app-design-builder/issues/220) (open), [#274 revise data protection mechanisms](https://github.com/nautobot/nautobot-app-design-builder/issues/274) (open, Feb 2026), [#72 design deployment diff view](https://github.com/nautobot/nautobot-app-design-builder/issues/72) (open since 2023), [#161 rollback to previous ChangeSet snapshot](https://github.com/nautobot/nautobot-app-design-builder/issues/161) (open).
- **Stale experiment:** branch `nk-add-excel-imports` (Apr 2024, one commit: "feat: Add Job 'Data population from Excel file'", 330 commits behind develop, includes an example xlsx). Evidence of NTC-side interest in lower-friction design input; never merged.
- **Note on `drift-manager/*` branches:** these are NTC's cookiecutter template-sync automation ("Rebaked from the cookie" in release notes) — *not* network drift management. Do not mistake them for reconciliation features.
- **Maintenance status (decision-relevant):** actively maintained. Releases: v2.1.0 (Oct 2024), v2.2.0 (Mar 2025), v2.3.0 (Dec 2025, LTM 2.4 line), v3.0.0 (Nov 2025, Nautobot 3.0 + Python 3.13, Bootstrap 5.3), v3.1.0 (Apr 2026: `next_ip` action tag, deployment-membership panels, code-injection fix), v3.1.1 (Jun 2026). Default branch pushed 2026-06-24. But adoption signals are weak: 15 stars, ~25 open issues, and the [Feb 2024 intro blog](https://networktocode.com/blog/design-builder/) (Bates/Adell/Kelly) remains the only substantive NTC blog post; it does not acknowledge authoring difficulty nor mention generation tooling. Also relevant: v3.1.0 docs added "how to enable deployment mode" (`design_mode` flag) — the lifecycle features (deployments, import mode, decommission) are opt-in.
- **YAML referencing model (feasibility of option b):** per [design_development docs](https://docs.nautobot.com/projects/design-builder/en/latest/user/design_development/), designs reference objects by query fields using Django-style `field__relatedfield` lookups (e.g. `platform__name: "Arista EOS"`), action tags `!create_or_update:<field>`, `!update:<field>`, `!ref` (store/retrieve objects, used for cable terminations, e.g. `!ref:spine_switch1:Ethernet1`), `!git_context`. Identification is by natural-key-like attributes, not UUIDs — so a generator emitting `!create_or_update` YAML from ORM traversal is mechanically feasible; cables need generated `!ref` bookkeeping. v3.1 docs added a caution to only use *unique* fields in update/update_or_create tags (issue #264) — a constraint a generator must respect.

## 2. Nautobot / NTC ecosystem

- **No published site-clone or site-template app/job exists.** GitHub repo searches ("nautobot clone", "nautobot site template", "nautobot design"), code searches ("export_site", "clone location", `create_or_update`+`yaml.dump`), and a full PyPI scan of ~110 nautobot-* packages found nothing that clones a location graph or generates designs.
- **[nautobot-deepcopy](https://pypi.org/project/nautobot-deepcopy/)** (v1.0.3, Jan 2025): the nearest thing — deep-copies a *single device* with all components; blanks asset tag and rack position, requires a rename. Instructive detail: it hard-codes a manual renaming policy, confirming the NetBox maintainer's point (below). Uses internal Nautobot APIs ("explicitly discouraged"), community-maintained. Same author family: nautobot-bulk-connect, nautobot-cable-utils, nautobot-type-reapply.
- **Nautobot core building blocks:**
  - *Clone button*: `clone_fields` shallow form pre-fill only — single object, no relations.
  - *[Export Templates](https://docs.nautobot.com/projects/core/en/stable/user-guide/platform-functionality/exporttemplate/)*: Jinja2 render of a queryset — could emit design YAML but is scoped to one content-type; no multi-model orchestration, so a Job is needed anyway.
  - *GraphQL*: read-only, one nested query can snapshot a location with racks/devices/interfaces/cables/prefixes — a natural "export" backend.
  - *`nautobot-server dumpdata --natural-foreign --natural-primary`*: full-DB JSON fixtures; [nautobot#3666](https://github.com/nautobot/nautobot/issues/3666) documents that GenericForeignKeys (TaggedItem, etc.) break natural-primary dumps; docs recommend pgdump for backup instead. Not site-scopable. A fixture-based snapshot/replay is a trap.
  - *Natural keys* ([Nautobot 2.0 release notes](https://docs.nautobot.com/projects/core/en/stable/release-notes/version-2.0/)): `instance.natural_key()`, `get_by_natural_key()`, `DEVICE_NAME_AS_NATURAL_KEY`/`LOCATION_NAME_AS_NATURAL_KEY` settings. Composite keys were later removed from user-facing REST API/UI, but the ORM API (usable inside a Job) remains — favoring a Job/ORM implementation over pure REST for the export/instantiate pair.
  - No "clone site/location" feature request even exists in nautobot/nautobot issues (searched "clone location", "clone site", "site template" — zero hits), i.e., nobody has pushed core for this.
- **NTC reverse-direction tools use diff-and-sync, never template generation:** [network-importer](https://github.com/networktocode/network-importer) (Batfish-based live-network→SoT sync) is in maintenance mode, folded into nautobot-device-onboarding (SSoT/DiffSync) for Nautobot 2.x. The SSoT app family shows NTC's house pattern for "existing state → Nautobot": adapters + diffsync, keyed on natural identifiers.
- **Abandoned snapshot/branching experiment:** nautobot-version-control (Dolt-backed branching for Nautobot) — last PyPI release Dec 2021, dead.
- **Active 2026 usage exemplar (forward generation, not reverse):** [SuperPOD Design Factory showcase](https://github.com/E-Conners-Lab/superpod-design-factory-showcase) (June 2026): private design-as-code system on Nautobot 3.0.8 + Design Builder 3.1.0 — requirements YAML → two composed designs (deployment shell + per-Scalable-Unit), `create_or_update` semantics for idempotent re-runs, plus a reconciliation loop diffing intended model vs. live snapshots. Demonstrates that serious Design Builder users treat designs as *code with a read-layer abstraction*, and that they validate via parity tests (same generators reading from templates or live Nautobot produce byte-identical output). Relevant pattern for validating any reverse-engineered design: regenerate from the created site and diff against the source export.
- **NTC workshops** ([AutoCon3 WS:D2](https://github.com/networktocode/autocon3-design-workshop), ONUG 2025) still teach hand-authored designs; no generation tooling appears in the materials.

## 3. Analogues in other ecosystems (and their failure modes)

### NetBox
- **[netbox-community/netbox#1994 "Ability to clone entire sites"](https://github.com/netbox-community/netbox/issues/1994)** — opened Mar 2018, closed by Jeremy Stretch within 2 days: "I don't think this is feasible to implement. You would have to contend with automatically renaming and renumbering myriad objects: racks, devices, prefixes, VLANs, IPs, circuits, etc. A non-trivial amount of additional logic is needed in the form of a renaming/renumbering policy, which NetBox cannot provide on its own. It would be much more practical to script out your own unique logic for replicating a site using either the REST API or local ORM." This is the single most decision-relevant piece of prior art: the *generic* clone problem was rejected by the most experienced DCIM maintainer as a policy problem, with per-org scripting endorsed as the practical solution. Eight years later, no NetBox site-clone plugin exists (searched July 2026).
- **[netbox-branching](https://github.com/netboxlabs/netbox-branching)** (NetBox Labs official, active): git-like schema-level branches for isolation/merge — *not* templating/cloning. Its open [issue #201 "Enable branch cloning with point-in-time replay"](https://github.com/netboxlabs/netbox-branching/issues/201) shows that even replaying a changelog onto a fresh copy is a nontrivial, still-unimplemented feature. The older core [staged-changes API](https://netboxlabs.com/docs/v3.7/netbox/plugins/development/staged-changes/) (v3.5–3.7 beta) was superseded by the branching plugin.

### Terraform / cloud IaC
- **[Terraformer](https://github.com/GoogleCloudPlatform/terraformer)** (the canonical "reverse Terraform" tool): **archived March 2026** after long maintenance decline ([status discussion #1253](https://github.com/GoogleCloudPlatform/terraformer/discussions/1253), ["Terraformer dead?" #1987](https://github.com/GoogleCloudPlatform/terraformer/issues/1987)). Known pain: per-resource state fragments needing manual merge, incomplete provider coverage, heavy post-generation refactoring; practitioner consensus that hand-writing config then importing is often easier ([Massdriver analysis](https://www.massdriver.cloud/blogs/generating-infrastructure-as-code-from-existing-cloud-resources)).
- **Terraform native**: import blocks + [`terraform plan -generate-config-out`](https://developer.hashicorp.com/terraform/language/import/generating-configuration) (v1.5, 2023) — still flagged **experimental** in 2026. Generated HCL is a "best guess" containing every readable attribute; HashiCorp's own guidance says strip computed values/defaults; output uses literal values, no variables/references/modules. Brownfield lesson: import aligns state, but you still see huge plans when config defaults don't match reality — making the config express *intent* is the human work.
- **AWS**: [CloudFormation IaC generator](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/generate-IaC.html) (native, Feb 2024; targeted resource scans added 2025) and community [former2](https://github.com/iann0036/former2) — both actively position output as review-and-correct starting points; circular dependencies and unexported properties are recurring issues. Notable: the cloud vendors ultimately built generation *natively into the platform* rather than leaving it to third-party tools — an argument for building the exporter as a first-class Job inside Nautobot.
- **Azure/GCP**: aztfexport and `gcloud` bulk export follow the same pattern (not verified in depth this session).

### Kubernetes
- `kubectl get -o yaml` → `apply` requires scrubbing server-populated fields: resourceVersion, uid, creationTimestamp, status, managedFields, last-applied annotation; failure mode is apply-time conflicts (e.g. "metadata.resourceVersion: must be specified for an update"). [kubectl-neat](https://fabianlee.org/2022/01/26/kubernetes-alternative-to-export-for-removing-internal-fields-from-yaml/) exists purely to clean exports; recommended alternative is generating clean manifests (`kubectl create --dry-run=client -o yaml`). `kubectl get --export` was deprecated/removed because maintaining a correct "export view" per resource proved untenable. Nautobot equivalents to scrub: id/UUIDs, created/last_updated, `_custom_field_data` defaults, and children auto-created by DeviceType component templates (exporting those and replaying causes duplicates/conflicts).

### Ansible
- No facts-to-playbook generator ever became mainstream. Facts capture observed state; playbooks encode intent, ordering, and idempotent desired state. Practitioner writing (e.g. [Level Up on reverse-engineering Ansible](https://levelupla.io/reverse-engineering-ansible-code/)) is blunt that state-to-code recovery cannot restore design intent with any guarantee. Red Hat's eventual answer was AI-assisted *authoring* (Lightspeed), not reverse-engineering.

### Cross-ecosystem failure-mode synthesis (what a Nautobot implementation must design around)
1. **IDs vs natural keys**: exports that reference DB IDs break on replay into another environment. Nautobot 2+ natural keys and Design Builder's name-based query syntax both mitigate this — but Tags/GenericForeignKeys are a known natural-key hole (nautobot#3666).
2. **Over-specific output**: naive exporters serialize every attribute including defaults, computed fields, and platform-generated children. Requires an explicit include/exclude schema per model (the kubectl-neat problem).
3. **Intent/parameterization gap**: no tool can infer *what varies per instance* (site name, prefixes, VLAN IDs, rack numbering, device names). Every successful analogue makes this a human-supplied policy — which is exactly the "minimal user input" form the instantiate Job should collect (NetBox #1994's "renaming/renumbering policy").
4. **Dependency ordering / determinism**: replay must be topologically ordered (location → racks → devices → interfaces → cables → prefixes/VLANs/IPs); Design Builder recently fixed create-before-delete ordering (#263), and its import mode assumes stable list ordering — ordering bugs are a live risk on both options.
5. **Round-trip drift**: generated artifacts go stale against the live site; the SuperPOD project's parity/diff loop and Terraform's plan-diff are the mitigation patterns. A "re-export and diff" validation job is cheap insurance.
6. **Abandonment risk**: generic reverse tools die (Terraformer archived, network-importer in maintenance, nautobot-version-control dead, staged-changes deprecated). Narrow, purpose-built, schema-pinned tools (export THIS org's site shape) have far better survival odds than a generic any-model design generator.

The gap is real; the analogues explain why it has stayed open (parameterization policy + per-schema maintenance cost), and they favor the purpose-built export/instantiate Job pair (option a), optionally emitting Design Builder YAML later once the object-graph traversal is proven.
